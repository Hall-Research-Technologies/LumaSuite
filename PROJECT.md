# PROJECT.md — LumaSuite Technical/Product Reference

This is the durable technical reference for LumaSuite: what is actually true
today. It was first established by direct source inspection on 2026-09-18 (commit
`f277352`) and has been brought up to date for the v1.1.0 release candidate
(2026-11-06): sections 2, 17, 18, 19, 20, 21 and 22 were rewritten then, and sections
36 and 37 describe Remote Access and the local port. Sections 5 to 16 and 23 to 35
describe the application as of the earlier passes they name; where they disagree with
sections 36 and 37 or with the code, the later section and the code win. See
[AGENTS.md](AGENTS.md) for the rules that govern *how* to work on this code.

Facts below are marked **VERIFIED FROM SOURCE** unless marked
**UNKNOWN — REQUIRES VALIDATION**.

## 1. Product purpose

**VERIFIED FROM SOURCE.** LumaSuite is a Hall Research device-management,
matrix-routing, video-wall, and firmware-upgrade console for:
- **LumaStream encoders/decoders** — Hall Research HDMI-over-IP hardware,
  model prefixes `HW-LUMA-E****` (encoder) / `HW-LUMA-D****` (decoder), e.g.
  `HW-LUMA-E4211`, `HW-LUMA-D4111`.
- **Atlona AT-OME-CS31** — an HDMI matrix switcher, treated as a distinct
  device role with its own protocol quirks (`lumaserver.py:1605`,
  `_is_switcher_device`).

It also embeds a "Producer" signage/streaming module (slate images, logo
overlay, scrolling ticker/OSD text, RTMP "Go Live" streaming config) —
sample runtime data (`producer_state.json`) suggests venue-signage /
promotional-ticker use (loyalty club, drink specials, sales-summit
announcements), i.e. this is used for AV signage/streaming deployments, not
just device provisioning.

## 2. Version / release state

**VERIFIED FROM SOURCE.** Current version: **1.1.0**. The one authoritative version is
`__version__` in `lumaserver.py`. Everything that shows a version reads it: the launcher
(`app_launcher.py` declares the same value and `tests/test_release_consistency.py` pins the
two together), `GET /api/app_version`, the Settings Application block, the User Guide
(fetched at run time, never typed into the page), the update check's `User-Agent`, a
backup's header, and the Windows version resource that `build_executable.py` generates from
`lumaserver.py` (the build keeps no version of its own). `README.md`, `CHANGELOG.md`,
`RELEASE_NOTES.md` and this file state it, and the same test fails if one drifts. No tag has
been created for 1.1.0 and nothing is published from this branch.

`CHANGELOG.md` carries one consolidated `v1.1.0` section (the earlier unreleased entries were
folded into it), then v1.0.8 and earlier. There is a runtime `GET /api/app_version` and a
`GET /api/version`: `/api/version` is the per-device firmware version query and
`/api/app_version` is the application's own version. They are different things.

## 4. Application startup

**VERIFIED FROM SOURCE.**
- `python lumaserver.py`: binds `127.0.0.1` by default (v1.1.0; `LUMA_HOST` overrides, and a
  non-loopback bind is treated as a network listener and gated -- see §36),
  `port=int(os.environ.get("LUMA_PORT","8089"))`, probing up to `PORT+100` if busy. Before v1.1.0 this
  bound all interfaces.
- `python app_launcher.py` (the packaged app's actual entry point, wrapped
  as `LumaSuite.exe`/`.app` by PyInstaller): sets `LUMA_DATA_DIR`, imports
  `lumaserver.APP`, runs it via `app.run(host='127.0.0.1', port=8090,
  threaded=True)` in a background thread (auto-incrementing port if busy; since LUMA-MA-010 through `luma_portcontrol`, with an optional fixed port -- see §37),
  then opens the default browser and shows a system-tray icon
  (`app_launcher.py:110-135, 376-417, 486-511`). This binds **localhost
  only**.
- `server.py` is a trivial WSGI-name shim, not an alternate entry point.
- README.md states the dev server runs on port 5000 — **this is incorrect /
  stale**; the actual default is 8089 (direct) or 8090 (launcher).

## 5. Frontend architecture

**VERIFIED FROM SOURCE — updated 2026-09-18, family-alignment pass.**
Vanilla JS/HTML/CSS, no framework, no bundler. Still a **multi-page app**
(each page a full HTML document), but as of this pass the shell/nav/gear
and Settings are shared, not copy-pasted:

| Page | Purpose |
|---|---|
| `ui/index.html` (all-inline JS) | Device Manager — landing page: scan, inventory table, firmware upgrade + non-destructive Check, reboot/remove/password-sync/NTP-sync/Slate-Manager bulk actions, CSV export |
| `ui/matrix.html` + `matrix.js` | Matrix Routing — decoder×encoder grid |
| `ui/producer.html` + `producer.js` | Production Studio — per-encoder live preview, video/audio/HDCP config, RTMP streaming, ticker, logo overlay, slate images |
| `ui/wall.html` + `wall.js` | Video Wall — grid-based wall builder, bezel/rotation, save/apply/import/export |
| `ui/manual.html` | User Guide — now in the main shell (has the same header/nav/gear as every other page); still also reachable from the Settings modal's About block |

### Shared modules (Hall Research application-family design, added 2026-09-18)

- **`ui/family.css`** — the token system: semantic surface/text/action/
  state custom properties (dark is the base on `:root`, fully restated
  under `html.light, body.light`), two density layouts
  (`html[data-density]="classic"|"compact"`), and the shared button/tab/
  toggle/pill/notice/modal/toast/confirm component CSS. Existing
  per-page variable names (`--bg`, `--card`, `--panel-2`, `--fg`/`--text`,
  `--muted`, `--accent`, `--border`, `--table`, `--danger`, `--ok`,
  `--video`, …) are aliased onto the new semantic tokens in the same
  file, so pre-existing page-specific CSS keeps working unchanged.
- **`ui/theme-boot.js`** — blocking script, first thing loaded in every
  page's `<head>`, applies theme/density/preset to `<html>` before first
  paint. Ten shipped colour presets (default/slate/cool/ocean/forest/
  warm/plum/rose/soft/contrast), adapted from OmniSuite's `appearance.js`
  presentation data. Reads the consolidated
  `localStorage["lumasuite.appearance"]` key (JSON `{theme, density,
  preset}`) when present, else falls back to the legacy `dark`
  boolean-string key every pre-existing `applyTheme()`/`toggleDark()`
  call site already read/wrote (those functions are unchanged and still
  work). Exposes `window.__lumaMirrorBody()`, called as the first
  statement inside `<body>` on every page, to mirror the theme class
  onto `<body>` too (some pre-existing CSS, e.g. `producer.html`, keys
  rules to `body.light`/`body.dark` specifically rather than the bare
  `.light` class that matches `<html>` alone).
  **Dark-mode preset defect (fixed 2026-09-18):** presets applied
  correctly in Light but not Dark. Root cause: `index.html`,
  `producer.html` and `matrix.css` each still declare the legacy
  back-compat aliases `--accent`/`--ok`/`--video` directly in their own
  embedded `:root{}` (their pre-family-system default), at the same CSS
  specificity as family.css's own `:root{--accent:var(--action-primary)}`.
  Dark mode is the bare `:root` in both places — a specificity tie broken
  by source order, and the page's own later `<style>` block wins,
  freezing the alias at its hardcoded default regardless of preset. Light
  mode only escaped this because family.css happens to write its
  override as the compound `html.light, body.light` selector, one
  specificity notch above a page's bare `.light` rule — not because
  presets were actually theme-aware there. Fix: `PRESET_TOKENS` now lists
  `--accent`/`--video` alongside `--action-primary`, and `--ok` alongside
  `--state-success`, so `applyPresetColors()` sets them directly via
  inline style, which always wins over any selector in either theme.
  `--danger`/`--border` were already listed this way and were never
  affected. No token values changed.
- **`ui/dialogs.js`** — rewritten (was previously a bare `alert()`
  replacement). Exposes `window.lumaConfirm(options)` (summary rows,
  version-scoped "don't show again" suppression, Escape/backdrop-click
  cancel, focus follows the cost — `danger`/`destructive` defaults focus
  to Cancel), `window.lumaDialog.{alert,confirm}` as compatibility
  wrappers, and `window.toast(message, "ok"|"error"|"info")`. This is
  the **one legitimate place** `window.alert` is reassigned; production
  UI must never call the native `alert()`/`confirm()`/`prompt()` —
  enforced by `tests/no_native_dialogs.test.js` (§18).
- **`ui/settings.js`** — one shared Settings module, injected into every
  page (previously `index.html` and `producer.html` each hand-maintained
  a near-identical, independently-drifting copy of the same modal;
  `matrix.html`/`wall.html`/`manual.html` had no Settings access at
  all). Sections: General (version + on-demand update check against the
  real GitHub Releases feed at `Hall-Research-Technologies/LumaSuite`,
  WS port, parallel uploads), Appearance (layout/theme/colour), 
  Authentication (username, Password, Fallback Password — §11), Firmware
  (folder chooser), Production Studio Assets (static-image/logo folder
  choosers), Application (About: copyright line + `/license` link; the
  "free for personal/business use" wording is deliberately omitted
  because no LICENSE file exists yet, §20). Reads/writes the same
  `/api/config` and new `/api/update_check` endpoints regardless of
  which page opened it.

Each page still fetches its own state fresh from the backend on load (no
client router/state store); *preferences* (appearance, column
visibility, last-selected adapter/wall/encoder, etc.) go through
`localStorage`. Backend-authoritative data (inventory, wall state,
producer assets) is explicitly never read from `localStorage`
(`index.html` comment: "always fetch from backend, never use
localStorage cache").

**Fixed, previously-flagged issues (both confirmed present before this
pass, at commit `f277352`):**
- `wall.html`/`manual.html` never applied the operator's light/dark
  preference at all (no theme script existed on either page) — always

  `theme-boot.js` above; verified with a before/after browser check
  (setting `dark=false` on `index.html`, then navigating to `wall.html`
  and reading its actual computed background colour).
- Production Studio's Settings gear button was hidden by a CSS rule
  (`#gear{display:none!important}`) — Settings was completely
  unreachable by mouse on that page. Removed; confirmed the button is
  now a real 36×36px element in the header.
- The company logo asset is designed for a dark background and was
  illegible on light mode on every page (no light-mode logo asset
  exists to swap in). Given a small dark backdrop chip in light mode via
  `family.css` rather than altering the asset.

## 6. Backend architecture

**VERIFIED FROM SOURCE.** Flask (`APP = Flask(__name__)`,
`lumaserver.py:100/108`). `flask-cors` was a declared dependency that was never
imported; it has been removed. Cross-origin write protection is a hand-rolled
same-origin check (`enforce_request_security_guards`,
`lumaserver.py:1321-1331`), which blocks cross-origin `POST/PUT/PATCH/
DELETE` to `/api/*` — this is CSRF mitigation, not user authentication.

`producer2_routes.py` is a Flask Blueprint registered at
`lumaserver.py:967-969`. A monkeypatch on `APP.add_url_rule`
(`lumaserver.py:957-965`) skips re-registration of a duplicate **endpoint
name**, but does not catch duplicate **URL rules** under different endpoint
names — see the `/api/producer2/state` double-registration bug below.

### Known bug: duplicate `/api/producer2/state` registration

`/api/producer2/state` is registered twice with two different endpoint
names: one pair of handlers (`get_producer_state`/`post_producer_state`,
`lumaserver.py:4593-4603`) reads/writes `producer_state.json`; a second pair
(`api_producer2_state`, `lumaserver.py:4605-4615`) reads/writes
`producer2_state.json`. Because the duplicate-guard only checks endpoint
names, both get registered in Werkzeug's routing map, but only the
first-registered rule is ever reachable — the second handler and
`producer2_state.json` are effectively dead code. Not yet fixed as of
v1.0.8; flagged here so it isn't mistaken for two live, distinct features.

## 7. Persistence / configuration

**VERIFIED FROM SOURCE.** All persistence is flat JSON files, no database.
Data directory resolution (`_default_data_dir`, `lumaserver.py:1085-1094`):
`%LOCALAPPDATA%\LumaSuite` (Windows) / `~/Library/Application
Support/LumaSuite` (macOS) / `~/.lumasuite` (Linux), overridable via
`LUMA_DATA_DIR`. On startup, legacy JSON files sitting beside the
source/exe are migrated into that directory (backing up any newer existing
file first).

| File | Contents | Notes |
|---|---|---|
| `units_cache.json` | Discovered device records: IP/MAC/serial/hostname/model/firmware/Dante/HDCP/EDID/per-role sub-objects | Written by `_persist_units_cache()`, merges memory+disk so unloaded fields aren't lost |
| `video_walls.json` | `{kind, version, walls:[...]}` — full wall/cell/decoder/encoder snapshots | No passwords stored here |
| `producer_config.json` | `{logos_path, imagestream_path, firmware_path, username, password}` | **Stores the shared device admin password in plaintext** |
| `producer_state.json` | Ticker text/config + RTMP stream presets **including stream keys** | Plaintext RTMP stream keys |
| `producer2_state.json` | Second RTMP/ticker state store | Effectively dead — see duplicate-route bug above |

All five files (plus `ui/localdata/producer_cache.json`) are explicitly
gitignored and confirmed **not tracked** in git — they are purely
runtime-generated local data, never committed.

**Correction (verified 2026-09-18, family-alignment pass):** in memory,
`cache_units` is a **dict keyed by IP address** (`cache_units[ip] = {...}`),
not a list — confirmed by reading assignment sites (`lumaserver.py`,
e.g. `cache_units[ip]["hdcp"] = ...`) and by a runtime `AttributeError`
hit while first writing `/api/firmware_check` against the wrong
assumption. `units_cache.json` **on disk** is still a JSON **array**
(confirmed: real file starts with `[`); the load path converts
array-on-disk to dict-in-memory. Code that reads `cache_units` must
iterate `.values()`/`.items()`, or index by IP directly — never assume
it's a list.

**Operational caution for anyone testing locally:** starting the app
with a fresh `LUMA_DATA_DIR` migrates whatever `units_cache.json`/
`video_walls.json`/`producer_config.json` sit beside `lumaserver.py` in
the repo root (real local network/device data, if you've scanned before)
into that new data dir — and loading `index.html` against it will then
trigger the background hostname/Dante/HDCP re-verification thread (§8)
for those real IPs. When testing against a throwaway `LUMA_DATA_DIR`,
pre-seed it with `units_cache.json` containing `[]` (and empty/default
copies of the other two) first, or real device I/O can be triggered
unintentionally from what looks like an isolated test run.

## 8. Discovery architecture

**VERIFIED FROM SOURCE.** There is **no mDNS/SSDP/UPnP/broadcast
discovery**. Discovery is operator-directed IP/CIDR range scanning,
triggered manually via `POST /api/scan` (`lumaserver.py:3139-3274`):

1. `_expand_targets()` parses a free-text target string into IPs — single
   IPs, CIDR blocks (capped at 4096 hosts), or last-octet ranges
   (`192.168.1.10-20`).
2. `_scan_one()` per candidate IP: fast TCP probe on 80/443
   (`_tcp_probe`, default 400ms timeout, env `LUMA_TCP_TIMEOUT_MS`), then
   opens a JSON-RPC WebSocket (`_ws_get_minimal`) and calls `System.Get` to
   pull model/serial/hostname/MAC/NTP; role is inferred from an explicit
   `Role`/`Type` field if the device provides one, else from model-name
   heuristics, else from protocol capability probing
   (`VideoMultiIpStream.Get` / `SelectVideoStream.Get`).
3. Scans run in parallel: `ThreadPoolExecutor` with up to `SCAN_WORKERS`
   (default 64, env `LUMA_SCAN_WORKERS`) workers, `SCAN_TIMEOUT` default
   1.2s (env `LUMA_SCAN_TIMEOUT`), up to 2 retries per host with a 0.1s
   delay if key fields come back empty.
4. Devices that don't resolve to encoder/decoder/switcher are dropped from
   the result.

Ongoing state refresh of *already-known* devices (`POST
/api/refresh_matrix_state`, 0.7s timeout, 32-worker pool) and `/api/cache`'s
background hostname/Dante/HDCP re-verification are **not** new-device
discovery — no periodic full-network scan loop exists; scanning is
on-demand from the UI only.

## 10. Device communication / protocol architecture

**VERIFIED FROM SOURCE.**
- **WebSocket JSON-RPC 2.0** is the primary control protocol
  (`websocket-client` package, `create_connection`). `_ws_url()` builds
  `ws://<ip>:<ws_port>/<path>` (or `wss://` only when `ws_port==443`) and
  tries candidate paths `/wsapp`, `/wsapp/`, `/ws`, `/ws/`, `/wsapi` until
  one connects. `_ws_call()` sends `{"jsonrpc":"2.0","id":...,"method":...,
  "params":...}`, discarding ID-mismatched frames (devices sometimes echo
  stale responses). `_ws_call_auth()` injects the configured password into
  `params.password`. CS31 switchers use a **different JSON-RPC shape** —
  params merged at the top level rather than nested under `"params"`
  (`_ws_call_switcher`), and some switcher calls must omit the password
  entirely (`_ws_call_switcher_no_password`).
- **HTTP via `requests`**: firmware upload (`/api/v1/fw_upload`, field
  `FIREWARE_FILE` — misspelling matches the device's own expectation),
  legacy session login (`/api/v1/auth/login`), legacy password change
  (`http://<ip>/change/password`, base64-encoded old/new password + a
  custom Bearer token), producer image/logo push
  (`/upload/priv`, `/upload/logo`).
- **Raw TCP sockets**: `_tcp_probe()` for reachability; a raw-socket
  fallback firmware-upload path for CS31 switchers that speak a non-HTTP
  protocol on port 80 (observed banner `"Upload data:"`), streaming the
  firmware file in chunks.
- **HTML scraping**: an `HTMLParser` subclass parses a device's own web
  page to auto-discover firmware-upload `<form>` actions/fields when the
  hardcoded endpoints don't work — a resilience mechanism against
  undocumented firmware UI variations.
- No Telnet, SSH, or MQTT usage anywhere in the codebase.

## 11. Authentication / password architecture

**VERIFIED FROM SOURCE.**
- **To devices**: password sent either as a JSON-RPC `params.password`
  field, or as a self-minted pseudo-"Bearer" token for legacy HTTP
  endpoints — constructed as `base64(json({create_time, role})) + "." +
  base64(json({password, username}))`. This is **base64, not a signed
  token** — superficially JWT-like but with no HMAC/signature. Some CS31 WS
  calls omit the password entirely.
- **Authentication (v1.1.0).** On the computer LumaSuite runs on there is still no sign-in: a request that
  arrived on the local listener is trusted by the socket. Remote Access (off by default, §36) adds accounts,
  sessions and CSRF for everything that arrives on a network listener, with every route classified and an
  unclassified route denied. Before v1.1.0 there was no authentication layer at all, and the only guard was the
  same-origin write check in §6 (a CSRF mitigation, not authentication).
- Single shared admin credential: `CONFIG["username"]="admin"`,
  `CONFIG["password"]="password"` hardcoded defaults, overridable via
  `producer_config.json` or `POST /api/config`.
- Password rule: `^[A-Za-z0-9!@#$%^&*]+$`, minimum length 6, enforced both
  client-side and server-side.
- Password is stored and transmitted **in plaintext** end-to-end — no
  encryption or hashing at rest (a SHA-256 hash is computed only for the
  read-only `/api/config` GET response, never stored). `GET
  /api/config?include_password=1` intentionally returns the plaintext
  password -- **to the local computer only since v1.1.0**: any other caller gets 403 `local_only`, and no remote
  response (administrator or user) carries a device password.
- A default-password flag (`is_default_password_in_use`) exists and is
  surfaced in the UI, but **nothing blocks operation** when the default
  password is still in use, except that RTMP status polling is disabled and
  firmware upgrade can return `error: "default_password_change_required"`.
  There is no code-level enforcement gate beyond that.

### Primary/Fallback device passwords (added 2026-09-18, family-alignment pass)

**VERIFIED FROM SOURCE.** `CONFIG["fallback_password"]` (default `""` =
disabled) is a second credential tried only after a **genuine credential
rejection** of the primary password — never on timeout, unreachable
device, malformed response, or an unrelated protocol error. Implemented
once, centrally, in `_resolve_ws_auth_response()`
(`lumaserver.py`, near `_ws_call_auth`), shared by `_ws_call_auth` itself
and by the Producer JSON-RPC proxy (`/api/producer/jsonrpc`) — previously
two separate password-injection paths, now one.

- **Rejection signal** (`_is_credential_rejection()`): a well-formed
  JSON-RPC error response whose message contains `"auth"`/`"password"`
  (case-insensitive) or whose code is `-32001`/`-32002`. This is the
  *same* heuristic `_ws_call()` already used, before this feature
  existed, to decide whether to log `"AUTHENTICATION FAILED"` — i.e. it
  was already derived from real LumaStream device behavior, not invented
  for this feature. `_ws_call()` returns `None` (not a dict) for every
  transport failure (timeout, refused connection, malformed/non-dict
  response), so those can never satisfy this check.
- **Verified device quirk**: `_ws_call_switcher()` (the CS31's
  top-level-params JSON-RPC shape) carries **no password field at all**
  in the current codebase — confirmed by reading its one call site
  (`_ws_set_hostname`, switcher branch). Primary/Fallback therefore has
  no effect on that path; it only matters for the standard nested-params
  shape (`_ws_call_auth`) that encoders/decoders use.
- **Credential memory**: `_device_credential_cache` (dict, `ip ->
  "primary"|"fallback"`, guarded by `_device_credential_lock`) is
  in-memory only, not persisted. A working credential is tried first on
  later calls for that IP rather than re-trying primary every time. Also
  mirrored onto `cache_units[ip]["password_source"]`
  (`"primary"`/`"fallback"`/`"failed"`, absent = never yet authenticated)
  so `/api/cache` and `/api/scan` responses carry it for free; the Device
  Manager table's **Password** column reads this field directly.
- **Audit logging**: every authenticated call logs one INFO line via
  `_audit_device_request()` with a redaction set
  (`_AUDIT_SECRET_FIELDS`) applied to the params — covers
  password/passwd/pwd/username/token/secret/fallback_password/etc.
- Settings exposes this as **Password** / **Fallback Password** (the
  established Hall-family terminology), both subject to the same
  `_is_allowed_password()` rule except that Fallback Password may be
  empty (meaning "not configured").
- Test coverage: `tests/test_password_fallback.py` (§18) — mocks
  `_ws_call` directly, asserts single-attempt-on-success,
  fallback-only-on-genuine-rejection, no-fallback-on-transport-failure,
  credential reuse, and the switcher no-password quirk.

### Auth/device-I/O correctness pass (2026-09-19)

**VERIFIED FROM SOURCE + REAL HARDWARE.** Two defects in the
2026-09-18 Primary/Fallback feature were found and fixed. Scope: the
resolver state machine and the Producer proxy's password handling only —
Password Sync's own mechanism (§12) was not touched.

**1. One-way fallback (the cached-Fallback recovery defect).**
`_resolve_ws_auth_response()`'s rejection-handling branch only ever
fired when `first_source == "primary"`. Once a device's cached source
became `"fallback"` (after a prior genuine Primary rejection), a
*subsequent* genuine rejection of that cached Fallback fell through to
the generic "reject and forget" branch with **no attempt to retry
Primary** — the credential cache was a permanent one-way latch, not the
optimization it was documented as. Symptom: a device that later needed
Primary again (e.g. an operator reverted the device's password, or
Fallback stopped being valid) would report Auth Failed forever, even
though Primary would have worked.

**Fix — corrected state machine (all in `_resolve_ws_auth_response()`):**
try the cached source first (default Primary if none cached, coerced
back to Primary if the cached slot is no longer usable — see duplicate
handling below); on a **genuine** rejection (`_is_credential_rejection()`,
unchanged and still the sole trigger), try the *other* configured
credential exactly once, symmetrically, regardless of which one was
tried first; a non-auth failure (timeout/refused/malformed/unrelated
JSON-RPC error) never triggers a second attempt and never touches the
cache. If both are genuinely rejected: this call reports Auth Failed,
and `_forget_credential_source_as_failed()` now also drops the IP from
`_device_credential_cache` (previously it only set the
`cache_units[ip]["password_source"]` display field) — so this is a
per-call outcome, not a latch; the very next call retries from Primary
and can recover if the device's credentials/settings change back.
Primary and Fallback resolving to the identical value
(`_fallback_usable()`) are treated as one unique credential and the
resolver never sends it twice.

**2. Producer proxy silently dropped a caller-supplied password
override.** `_resolve_ws_auth_response()` unconditionally overwrote
`params["password"]` with the resolved Primary/Fallback value, for
every caller, including one that had already put its own password in
`params`. This is a real, shipped code path, not a hypothetical: the
Reboot button (`ui/index.html`, `rebootSelected()`) sends
`params: { password: appConfig.password }` on `Platform.Reboot` — its
own idea of the current admin password — which was being silently
discarded and replaced with whatever the resolver's cache preferred
(invisible in the common case where they agree, but wrong whenever a
device's cached source was Fallback and the operator's UI still held
Primary).

**Fix:** `_resolve_ws_auth_response()` takes a new
`honor_caller_password_override: bool = False` parameter. Only
`api_producer_jsonrpc()` (`/api/producer/jsonrpc`) passes `True`. When
set, and the caller's `params` already contains a `"password"` key,
that value is popped out and sent verbatim in a single attempt — no
Primary/Fallback rotation, no credential-cache read or write. The
override is operation-scoped: it never mutates `CONFIG["password"]`/
`CONFIG["fallback_password"]` and is never remembered as a device's
known-good source (no existing rule calls for treating it as one).
`_ws_call_auth()`'s internal call sites never set this flag, so the
several places that redundantly pre-populate
`params["password"] = CONFIG.get("password", ...)` before calling
`_ws_call_auth` are completely unaffected — their password key
continues to be resolved/overwritten by Primary/Fallback exactly as
before. Because only the literal `"password"` key is ever touched, a
differently-named field the caller sends alongside it (e.g. a
hypothetical `LoginPassword.Set` new-value field) passes through
untouched — the authentication credential and a new-password *value*
can never be confused as long as they use different keys, and this
proxy never special-cases `LoginPassword.Set`'s params shape (no
verified real wire format for it exists anywhere in this codebase —
nothing currently calls it — so none was invented here).

**Settings-change cache invalidation.** A new
`_invalidate_credential_cache(reason)` clears all of
`_device_credential_cache` (and the `password_source` display field on
every cached unit) whenever `POST /api/config` actually changes
`password` or `fallback_password` to a different value, and whenever
`POST /api/upgrade`'s legacy inline `CONFIG["password"]` override
changes it. A no-op write (same value) does not invalidate. This never
stores or logs password material — only ever the string `"primary"` or
`"fallback"` was ever cached, and invalidation just clears that label.

**Real-hardware note (verified, not assumed):** on the real
HW-LUMA-D4111 decoders available for this pass, the standard nested-
params WS `.Get` methods that were probed (`System.Get`,
`VideoOutTiming.Get`) returned a valid `result` regardless of whether
the password field sent was correct — this firmware does not appear to
enforce authentication on those particular read calls at all, so a
genuine credential rejection could not be reproduced live through them
even after actually rotating the device's real password via the
proven `/api/producer/change_password` HTTP mechanism. (Two other
`.Get` methods, `EdidInput.Get`/`HdcpAnnouncement.Get`, returned a
`-32603 Internal Error` regardless of password correctness too —
confirmed unrelated to credentials, a separate pre-existing quirk on
this model, not something this pass introduced or masked.) The
corrected state machine's actual rotation behavior — including the
cached-Fallback recovery fix — is verified by automated,
hardware-fenced tests (`tests/test_credential_recovery.py`) using
mocked rejection responses, which is the only way to reliably exercise
"genuine rejection" given this observed device behavior.
- Test coverage: `tests/test_credential_recovery.py` — the resolver
  transition matrix (no-cache / cached-Primary / cached-Fallback ×
  success / genuine-rejection / non-auth-failure, both-rejected,
  recovery after a prior Auth Failed, duplicate credentials, missing
  Fallback, Settings-change cache invalidation) and the Producer
  override matrix (override reaches the outbound call verbatim, is a
  single attempt, never mutates Settings/cache, is never echoed or
  logged, `LoginPassword.Set` keeps the auth key and any differently-
  named new-value field distinct, malformed requests, unrelated
  methods, and CS31-style calls are unaffected).

## 12. Password Sync

**VERIFIED FROM SOURCE.** There is **no backend function or route literally
named "password sync."** It is a frontend-orchestrated bulk operation
entirely in `ui/index.html`:

1. Operator opens the "Password Sync" modal, enters current + new password.
2. `getPasswordSyncEligibleIPs()` filters targets to encoder/decoder roles
   only — **switchers are explicitly skipped**.
3. `submitPasswordSync()` calls `POST /api/producer/change_password`
   **sequentially, once per eligible device** — no batching/parallelism.
4. That backend route (`lumaserver.py:4264-4332`) mints a Bearer token and
   POSTs `{username, newpassword, oldpassword}` to
   `http://<ip>/change/password` on the device; success = HTTP 200 + JSON
   `{"code":0}`.
5. **Only if all devices succeeded** does the frontend also call `POST
   /api/config` to update LumaSuite's own stored password to match. Partial
   failure is reported to the user ("Set on X, failed on Y") but LumaSuite's
   stored password is left unchanged in that case — **there is no
   device-side rollback** of the devices that did succeed.

Both client-side and server-side password-strength validation run before
any device call is made.

**Status as of the 2026-09-18 family-alignment pass: unchanged by
design.** The mechanism above (sequential, encoder/decoder-only,
success-gated stored-password update) is explicitly preserved — the
family alignment pass restyled the Password Sync modal's presentation
only. A functional redesign remains deferred, separate work.

**Confirmed unaffected by the 2026-09-19 auth/device-I/O correctness pass
(§11).** Password Sync's device-mutating step (`POST
/api/producer/change_password`, step 3-4 above) is a wholly separate
Flask route from the Producer JSON-RPC proxy (`/api/producer/jsonrpc`)
that pass fixed — it mints its own Bearer token and POSTs directly to
the device's legacy `/change/password` HTTP endpoint with an explicit
caller-supplied `oldpassword`/`newpassword`, never going through
`_resolve_ws_auth_response()` at all. It was never subject to either
defect fixed in §11 and required no change here.

## 13. Firmware architecture

**VERIFIED FROM SOURCE.**
- **Discovery**: `_firmware_search_roots()` checks, in order, the
  configured `firmware_path`, the bundled `<app>/firmware` directory, and
  `<DATA_DIR>/firmware`. `_collect_firmware_files()` lists `*.tar.gz` files;
  `GET /api/files` exposes `{filename, mtime}`, deduplicated by filename
  preferring newest mtime. **No pre-upload version-vs-device comparison
  exists** — the UI just lists files by mtime; the operator picks manually.
- **Upload/upgrade flow** (`POST /api/upgrade`): TCP precheck, best-effort
  login, then branches by device type:
  - Encoder/decoder: HTTP multipart upload to `/api/v1/fw_upload`, then a
    JSON-RPC trigger call.
  - CS31 switcher: multi-attempt HTTP upload (`_upload_fw_cs31_multi`,
    several endpoint/field/content-type combinations) falling back to the
    raw-socket path (`_upload_fw_cs31_socket`) on failure; then
    `_monitor_cs31_upgrade()` polls for up to 10 minutes through states
    `sending_file → updating → rebooting → confirm_version → success`,
    detecting reboot via reachability loss/regain and confirming the new
    version post-reboot (up to 4 checks, 3s apart) against both the cached
    baseline version and the version implied by the firmware filename.
- **Standalone fallback tool**: `firmware/upload.py` — a bare CLI script
  (`--ip`/`--file`) doing a single multipart POST to `http://<ip>/upload`,
  independent of the main server's more elaborate logic. Treats a
  connection drop during upload as an expected "device is flashing"
  condition, not a failure.
- Firmware `.tar.gz` files in `firmware/` are **local operator content**:
  gitignored, not committed, not bundled into the packaged executable by
  either `build_executable.py` or (the unused) `LumaSuite.spec`.

### Non-destructive firmware Check (added 2026-09-18, family-alignment pass)

**VERIFIED FROM SOURCE.** `POST /api/firmware_check` (`{"ips": [...]}`)
answers "is a newer firmware available?" **without starting an upgrade
and without any device I/O** — it only compares
`cache_units[ip]["version"]` (the device's last-known reported version)
against the highest version parseable from local firmware filenames
matching that device's model prefix
(`_highest_local_firmware_version()`/
`_extract_version_from_firmware_filename()`, requiring the version to be
immediately preceded by a literal `V`/`v` so it can't match digits that
are part of the model name itself, e.g. the "4211" in
"HW-LUMA-E4211-WHOLE-V1.0.2.3.tar.gz"). States returned, one per IP:
`update_available`, `up_to_date` (including a device whose reported
version is *ahead of* the local file — not an error), `unknown` (no
local firmware file matches that model, or the device isn't cached), or
`unable_to_check` (the device's own current version isn't known). The
Device Manager's **Check Local Firmware Files** button (renamed from
"Check Firmware" in the 2026-09-19 release-preparation pass, §34 below --
label/tooltip only, behavior unchanged) surfaces this per row as a badge
next to the Version cell; it never affects the actual upload/upgrade flow
described above.

## 14. Routing/control functionality

**VERIFIED FROM SOURCE.**
- **Matrix routing** (`POST /api/route_matrix`): validates both IPs, reads
  the encoder's current stream name (live, falling back to cache), then
  sets the decoder to that stream — via a switcher-specific setter (no
  password, top-level params) for CS31 decoders, or `SelectVideoStream.Set`

  parallel-polls all cached units to keep the UI in sync with real state.

  export/refresh/source/bezel/rotation/apply endpoints. Device-mutating
  setters are "if needed" idempotent — they only push a value when the
  device's currently-reported value differs. CS31 is categorically
  ineligible (§24). Spatial drag-and-drop routing, added 2026-09-18, is a
  UI layer over this same subsystem — see §25. `GET /api/video_wall/detect`
  (§26) is a read-only addition that reconstructs an existing wall
  configuration from live decoder state on page load, verified against
  real hardware; it never writes a device or `video_walls.json`.
- **HDCP**: `POST /api/set_hdcp` → `HdcpAnnouncement.Set` (encoder input) or
  `OutHdcpAnnouncement.Set` (decoder output).
- **Dante audio power**: `POST /api/set_dante_power` →
  `SystemFuncDantePowerStatus.Set`.
- **Hostname/streamname/NTP/reset**: direct per-device WS JSON-RPC pushes,
  with hostname/streamname format validation.
- **Producer/signage**: slate image upload/default, an allowlisted JSON-RPC
  proxy (`/api/producer/jsonrpc`, restricted to `PRODUCER_ALLOWED_METHODS`,
  not an open passthrough), image/logo push via the producer2 blueprint.

## 17. Packaging / build process

**VERIFIED FROM SOURCE.** Two build configs exist; only one is live:
- `build_executable.py` is the **actual build mechanism**, used by CI and documented in
  `BUILD_STANDALONE.md`. It dispatches by platform argument or `platform.system()`: Windows
  (`--onefile --windowed`, Windows version resource generated from `lumaserver.py`'s
  `__version__`), macOS (`--onedir --windowed`, **one architecture per build**, taken from
  `PYI_MACOS_ARCH` or the machine, bundle identifier `com.lumasuite.app`; it is not a universal
  binary), Linux (`--onefile --windowed` plus a generated `.desktop` launcher and install
  script). The entry script is `app_launcher.py` in every case. Every build adds `ui/`,
  `hallway.png`, `atlona.png`, `licenses/` and `THIRD_PARTY_NOTICES.md`, and refuses to start
  if the last two are missing. No firmware or credential files are ever added as build data.
- `LumaSuite.spec` (tracked in git despite `.gitignore`'s generic `*.spec` rule pre-dating it) is
  **stale/unused**, not referenced by `build_executable.py` or CI, and has drifted from the real
  build. Don't assume edits to it affect the shipped executable.
- **Third-party notices**: `tools/collect_licenses.py` copies the licence files of every
  distribution that is inside the executable (the set was read from a real PyInstaller PKG/PYZ
  table of contents, not guessed from the lock) into `licenses/`, writes `licenses/MANIFEST.json`
  and `THIRD_PARTY_NOTICES.md`, and `--check` verifies they still match the installed packages.
  The server serves them at `/license` and `/licenses/<package>/<file>` (public, and only paths the
  manifest lists). `tests/test_notices.py` asserts the lock, the manifest, the notices and the texts
  agree.
- CI: `.github/workflows/build-cross-platform.yml`, matrix over `windows-latest`, `macos-26-intel`,
  `macos-26` and `ubuntu-latest`, triggered by a push to `main`, a `v*` tag or manual dispatch.
  Steps: install the lock, `py_compile` every server module, run every Python suite, `node --check`
  the UI scripts and run every Node suite, then build, upload artifacts and package
  `LumaSuite-<tag>-windows-x86_64.zip`, `-macos-x86_64.zip`, `-macos-arm64.zip` and `-linux-x86_64.tar.gz`. An `identity`
  job runs first (`tools/release_guard.py identity`, tested by `tests/test_release_guard.py`): a tag must be exactly
  `v` plus `__version__` and sit on `origin/main`, otherwise the run stops; a branch push or dispatch is a diagnostic build
  that cannot publish. A valid tag creates a **draft** GitHub Release (never published automatically) from those
  archives, after `release_guard.py inspect` checks the exact asset set and contents, with a `SHA256SUMS.txt` written
  from the final bytes. A person publishes the draft. The update check additionally refuses any release whose tag is
  not exactly `vX.Y.Z`, any draft or prerelease, and any asset not named for that exact tag
  (`tests/test_update_production_identity.py`). `tests/test_release_consistency.py` fails if a
  suite exists that the workflow does not run. `tests/smoke_packaged.py` starts a built artifact and
  is run by hand; CI does not run it.

## 18. Test architecture

**VERIFIED FROM SOURCE, updated for the v1.1.0 release candidate.** No test framework and no
`package.json`: tests are plain scripts. `python run_tests.py` runs every suite the way CI does,
one process per suite (because `lumaserver` is imported once per process and holds module-level
state), and totals the results. It runs `tests/test_*.py` with Python and `tests/*_test.js` and
`tests/*.test.js` with Node.

- **Hardware fence.** `tests/_fence.py`, installed by `tests/_support.py` before anything imports
  `lumaserver`, refuses every socket that is not loopback and points the data folder at a scratch
  directory, so no suite can reach a device, the network or an operator's real files, however it is
  run. `tests/test_fence.py` proves it. Fixtures use documentation addresses and locally
  administered MACs; a bench address never appears in a test.
- **Python suites** cover the access gate (every route classified), accounts and sessions, the
  certificate identity, routing and verification, Display Group and saved-wall identity checks,
  the scan merge, the restore stages and sessions, backup bounds, the update check's archive
  matching, the licence notices, release consistency and dependency hygiene, and the Video Wall and
  Producer logic.
- **Node suites** run the UI scripts in a DOM stub (`tests/_dom.js`) and check, among other things,
  that production UI never calls a native `alert`, `confirm` or `prompt`
  (`tests/no_native_dialogs.test.js`), that the shell is the same on every page, the Production
  Studio logo controls, the Device Manager table, the routing pages and the Settings dialog.
- **Mutation harnesses** (`tests/mutate_security.py`, `mutations_*.py`) break a predicate on purpose and

- `tests/smoke_packaged.py` and `tests/smoke_remote_packaged.py` start a built executable; by hand.
- Every suite is run by the release workflow, and `tests/test_release_consistency.py` fails when a new
  one is not added to it.

## 19. Hardware/network communication boundaries

**VERIFIED FROM SOURCE — and this is the most important finding for future
test work.** There is **no abstraction layer** between route handlers and
device I/O. `requests`, `socket`, and `websocket-client` calls are made
**directly inline** inside route handlers and their private helpers, all
reading module-level global state (`CONFIG`, `cache_units`). There is no
injectable "device client" seam, no dry-run/mock mode, no fixture device
server. Any future Python test that drives a route touching device I/O
**will attempt real network calls** unless it explicitly monkeypatches
`_ws_call`/`_ws_call_auth`/`_ws_call_switcher`/`_tcp_probe`/
`requests.post`/`requests.get`/`socket.socket`/`socket.create_connection`/
`websocket.create_connection`, or targets addresses guaranteed to fail to
connect. `CONFIG` mutation is global and process-wide, so parallel tests
would also interfere with each other's credentials/timeouts.

**The automated tests reach this boundary only through the fence.** Because there is no
injectable device client, `tests/_fence.py` is the guarantee: a test that would open a
non-loopback socket fails instead, and a mutating device call fails the test. The test
entry point installs it, not each test.

## 22. Known limitations (evident from code/docs)

**VERIFIED FROM SOURCE / repo docs.**
- No `TODO`/`FIXME`/`HACK` markers in `lumaserver.py` — limitations are
  self-documented in `README.md`'s Troubleshooting section and
  `CODE_REVIEW_FIXES.md` instead.
- `CODE_REVIEW_FIXES.md` records three previously-fixed issues (O(n²)
  MAC-address search → indexed lookup; inconsistent JS event-handler
  patterns; an `innerHTML` XSS risk in ticker rendering → fixed via
  `createElement`) and a still-open "Future Improvements" backlog: add
  DOMPurify, add CSP headers, add server-side input validation for RTMP
  URLs/ticker text length. None of the backlog items are implemented as of
  v1.0.8.
- The duplicate `/api/producer2/state` registration (§6) is a known,
  unfixed bug as of this audit.
- The README used to document endpoints and a port (`/api/units`, `/api/route`, `/ws/<device_ip>`,
  5000) that never existed in this code; it has been rewritten and no longer lists an API. The real
  endpoints are in `lumaserver.py` and `luma_access.ROUTES`; there is no inbound `/ws/<ip>` route
  (WebSocket connections are made outbound from the server to devices).
- Request bodies are read by one helper (`luma_request.json_object`): a non-object JSON body is refused with 400 on every JSON
  route, a few text/list fields are kind-checked in one table, and `tests/test_request_bodies.py` posts the bad bodies to every
  POST route in the route table, as a local caller, a remote administrator, a remote user and an anonymous caller, with the
  hardware fence on. Clear Units is the one command that acts on an empty object by design (the server decides from its own
  state); it is listed in that test.
- Identity shape is decided by `luma_mac.py`; no other module may strip separators to guess a MAC.
- The network listener checks Host (`luma_remote.host_allowed`), sends `LumaSuite` as `Server`, and adds nosniff, frame denial
  and no-referrer to remote responses; there is deliberately no Content-Security-Policy.
- The generated Remote Access private key inherits the data folder's access list on Windows. A remote administrator reaches
  the device-changing endpoints by design. A restricted User's verified wall route rewrites the saved wall's `source_id`
  (documented in code; a product decision for the owner).
- Operational limits of the v1.1.0 release candidate: `GET /api/remote_access` performs a network-adapter
  lookup and can take a few seconds; there is **no single-instance lock** (a second copy takes the next free

## 24. Video Wall: CS31 is not an eligible participant

**DURABLE PRODUCT RULE, verified from source and enforced at a single
choke point.** The Atlona AT-OME-CS31 switcher has no Video Wall
capability. It must never appear as a Video Wall source, a Video Wall
decoder, a drag/drop target, or an apply target — in the spatial UI, in
the legacy per-cell dropdowns, or in any saved/imported configuration.

This is enforced in `_vw_units_snapshot()` (`_vw_is_cs31()` checks
`type`/`role`/`model` text for `"cs31"` and skips the unit entirely before
either the encoder or decoder classification runs), which is the single
function every Video Wall code path uses to resolve devices
(`_vw_find_unit()` searches exactly its combined encoders+decoders list).
Because of that, a CS31 referenced by a decoder ID — whether from live
discovery or from stale/malformed saved data — resolves as "not found"
everywhere: `_vw_apply_source_cell`/`_vw_apply_bezel_cell`/
`_vw_apply_rotation_cell` refuse it before any WS call is attempted, with
`_vw_cs31_reason()` producing a clear "CS31 switchers cannot participate
in a Video Wall" message (rather than the generic "not discovered") when
the referenced ID is a real, cached CS31. No Video Wall WS method is ever
sent to a CS31, regardless of how it got into a wall's saved `cells`.
General CS31 support elsewhere in LumaSuite (Matrix routing,
switcher-specific setters, Production Studio) is untouched — this
restriction is scoped to Video Wall only.

## 25. Video Wall: spatial routing, 2x2 first (added 2026-09-18)

Redesigned interaction, modeled on OmniSuite Multiview's *UI/interaction
pattern* only — draggable source cards, a canvas of drop targets, a single
CSS class toggle for pre-drop highlighting, a flat `{cellKey: sourceId}`-
style assignment map re-rendered in full on every change. OmniStream's
underlying device model (multi-window composition on one decoder) is the
opposite topology from LumaSuite's wall (one source spanning multiple
physical decoders) and none of it was ported — see the completion report
for the explicit reused-vs-rejected breakdown.

**Existing device model reused as-is.** `StandardVideoWallInfo.Set` takes
`vwmatrix`, a `"{rows}_{columns}_{row}_{column}"` string, decoupled from
source selection (`SelectVideoStream.Set` is a separate call). Nothing
about this ties `rows`/`columns` to "the whole physical wall" — that was
only ever how the pre-existing software always called it. A decoder's
wall-position is a self-contained fact the device is told; two decoders
can be part of a plausible 1x2 "sub-wall" every bit as validly as four can
be part of a 2x2 one.

**The region model.** `wall.regions` is an additional, optional array
alongside each cell's existing `source_mode`/`override_source_id` — a
region never replaces those fields, it just takes precedence when a cell
belongs to one (`_vw_effective_matrix_and_source()` /
`effectiveGeometryAndSource()` in wall.js check region membership first,
fall through to the pre-existing wall/override logic otherwise). A region
is `{id, cells:[{row,column},...], source_id, source_snapshot}`; its
local `rows`/`columns`/`row`/`column` for a given cell are computed from
the region's *own* cell set, not the wall's, via `_vw_region_geometry()`
(backend) / `regionGeometry()` (frontend) — this is what makes a 2-cell
region a valid independent 1x2 sub-wall. `_vw_clean_regions()` /
`cleanRegions()` refuse anything that isn't a complete rectangle within
the wall's current bounds, and resolve any overlap by rejecting the later
region wholesale rather than splitting a cell. Regions are validated and
persisted through the existing `_vw_clean_wall()`/`normalizeWall()`
pipeline, so `/api/video_wall/save` round-trips them like any other field.

**The nine 2x2 targets.** Four single-display targets are the existing
per-cell override mechanism unchanged. The four-display "center" target
(the whole wall) is deliberately *not* modeled as a region — it reuses
`wall.source_id`/`source_mode="wall"` exactly as the toolbar's "Wall Video
Source" dropdown always has, because that IS the whole-wall case. Only the
four two-display boundary targets (top/bottom/left/right) are genuine
regions — the one case the pre-existing per-cell model could not already
express. `/api/video_wall/source` gained a `scope:"region"` alongside its
existing `"wall"`/`"cell"` scopes, resolving targets from
`wall.regions[].cells` the same way `"cell"` resolves from `row`/`column`.

**The crosshair.** A small 5-zone overlay (`ui/wall.html`'s
`#wallCrosshair`, a 3x3 CSS grid using only the 4 edge cells + center, the
4 corners left empty) is positioned by JS (`positionCrosshair()`) at the
measured intersection point of the rendered 2x2 grid — not a hardcoded
fraction — so it tracks `WALL_CELL_WIDTH`, compact mode and gap changes.
Its zones are `pointer-events:none` and invisible until a drag begins
(`.wall-crosshair.dragging`), so it never intercepts an ordinary click on
a monitor; hit-testing (`hitTestTarget()`) uses
`document.elementFromPoint()`, which correctly skips
`pointer-events:none` elements, so normal clicks pass through to the cell
beneath with no special-casing needed. Only exists for a 2x2 wall
(`currentWall.rows === 2 && currentWall.columns === 2`); every other wall
size keeps exactly its pre-existing single-cell-only drop behavior.

**UI restructure.** The per-cell Decoder/Source/Rotation `<select>`
elements were moved out of the grid cell (which now renders as a monitor
visual — a dark "screen" face showing the effective source, R{row}C{col}
badge, decoder identity as a small secondary line) and into the "Selected
Display" side panel, now editable rather than read-only. This is the
fallback path required to stay available: an operator who never drags
anything can still assign every cell exactly as before, just from the
side panel instead of the grid. A cell that is part of a region shows a
"Detach from region" button there, which dissolves the whole region
(a region needs ≥2 cells by construction, so "detach one" always means
"end the region") and leaves the clicked cell with an explicit override of
the region's former source.

**Deliberately not implemented — proposed only.** Larger-wall spatial
targets (3x3, 4x4, arbitrary rectangles) were not built. The `region`
shape (`{id, cells: [...], source_id}`) already generalizes — nothing
about `_vw_clean_regions()`/`_vw_effective_matrix_and_source()` assumes
2x2 — but the *drop-zone interaction* for choosing an arbitrary rectangle
on a larger grid (how many boundary/intersection targets, how they're
discovered/highlighted) was explicitly deferred pending design approval;
seeing the crosshair-of-5 approach scale past 2x2 is not obvious (a 3x3
wall has far more than 5 interesting sub-rectangles) and invents no
interaction model here.

## 26. Video Wall: detecting an existing configuration (added 2026-09-18)

**Verified live against real hardware** — four development decoders
(`ul`/`ur`/`ll`/`lr`, hostnames matching their physical position) already
configured as a working 2x2 wall, plus a real CS31 switcher
(`AT-OME-CS31-SA-HDBT`) on the same network.

### What the hardware actually returns

`StandardVideoWallInfo.Get` → `{"vmenable": bool, "vwmatrix":
"rows_columns_row_column"}` (e.g. `"2_2_1_1"`). This is the *only* field
that reliably identifies wall topology and membership. Two findings that
contradicted the reasonable-sounding assumption that an active wall's
decoders would agree on everything else:

- **`vmenable` is not uniform across a genuinely working wall.** The real
  four-decoder wall read `ul=false, ur=true, ll=true, lr=false` — half the
  members reported `vmenable=false` while all four carried complete,
  non-conflicting 2x2 coordinates. Cross-referenced against
  `_vw_apply_source_cell` (§25/§14), `vmenable` is what LumaSuite's own
  software sets when `source_mode="wall"` vs `"override"` — it describes
  whether *this decoder is currently showing the wall-cropped source right
  now*, not whether it belongs to the wall. A decoder can be a fully
  configured topological member while independently overridden to a
  different source at this moment, and the real hardware demonstrates
  exactly that.
- **Streamname is not uniform either.** Three of the four read
  `"stream-main"`; one (`ll`) read `"room-a"` — including one of the two
  `vmenable=true` decoders. Source routing was not a reliable membership
  or consistency signal on this real wall, so it is surfaced to the
  operator per-cell but never used for grouping or status.
- **No explicit wall identifier exists anywhere in the protocol.**
  Membership is inferred, not read from a wall-ID field, because there is
  no such field.
- **CS31 has no Video Wall capability at the protocol level, not just by
  LumaSuite policy.** A live probe of `StandardVideoWallInfo.Get` against
  the real CS31 on this network returned JSON-RPC error `-32601 Method not
  found` — confirming §24's exclusion rule matches genuine hardware
  behavior, not just a naming convention this software imposes.

### The inference algorithm — `_vw_detect_walls()`

Pure function, no device I/O (the caller, `GET /api/video_wall/detect`,
does the reading). Takes a list of per-decoder state (as `_vw_read_decoder`
already produces) and:

1. A decoder whose `vwmatrix` doesn't parse into four positive integers
   (unreadable, absent, or a boolean/zero coordinate) is **unassigned**.
2. A decoder whose `row`/`column` exceeds its own claimed `rows`/`columns`
   is **invalid** — reported by itself, never forced into a group.
3. Remaining decoders are grouped by their own `(rows, columns)` — the only
   shared characteristic the protocol actually exposes. This is a
   conservative choice: two physically distinct walls of the *same*
   dimensions are indistinguishable from this data alone (streamname
   already proved unreliable for this, per above), so nothing here
   attempts to split same-size groups further — see "Multiple walls" below.
4. Within a group, a coordinate claimed by more than one decoder is a
   **conflict**, naming every claimant; it is never silently resolved by
   picking one, and that coordinate is excluded from `members`.
5. A group with all `rows x columns` coordinates present and no conflicts
   is **complete**; missing some (and no conflicts) is **partial**, naming
   exactly which coordinates are missing.
6. A group that reduces to one decoder (`rows*columns == 1`) is not a wall
   — the decoder is reported **unassigned/standalone** instead, matching
   the spatial UI's own treatment of a single cell as an override, not a
   one-cell wall.

Decoder eligibility (CS31 exclusion) happens entirely upstream, in
`_vw_units_snapshot()` (§24) — `_vw_detect_walls()` has no model/type
awareness of its own by design, so the exclusion cannot drift out of sync
with the one enforced everywhere else.

### Multiple walls

Groups of different `(rows, columns)` are automatically separate
candidates with no extra logic. Groups of the *same* size cannot be
reliably split without an explicit wall identifier the protocol doesn't
have; a duplicate coordinate inside one group is reported as a conflict
rather than guessed into two walls. This is a genuine, documented
limitation, not an oversight — see the real hardware findings above for
why streamname (the one plausible tiebreaker) is not trustworthy either.

### `GET /api/video_wall/detect` — read-only, called on page load

Reads every eligible discovered decoder (parallel, `.Get` calls only —
the identical transport pattern `/api/video_wall/refresh` already uses),
runs `_vw_detect_walls()`, and best-effort matches each detected candidate
against an existing saved wall in `video_walls.json` by `(rows, columns)`
+ identical decoder-ID set (regardless of which coordinate each currently
claims). **Writes nothing** — not to a device, not to `video_walls.json`.
The Video Wall page calls this once after its normal load and shows a
banner (`#detectionBanner`) only when a candidate isn't already the
currently-open wall. "View Detected Layout" either opens the matched saved
wall or builds an in-memory (unsaved) wall from the detected members —
either way, nothing is persisted until the operator explicitly presses
Save, per the family's existing save/apply model.

### Verified end-to-end against real hardware

Live sequence, all four steps against the real decoders: (1) `GET
/api/video_wall/detect` on the known-good wall returned `status:
"complete", 4/4, matched_saved_wall: "2x2"` with the correct
decoder→position mapping (`ul→R1C1, ur→R1C2, ll→R2C1, lr→R2C2`) and each
member's real rotation/source/bezel; (2) the Video Wall page, opened on a
*different* saved wall, showed the detection banner and "View Detected
Layout" correctly switched to the matching saved "2x2" wall with all four
cells populated from live device state; (3) a deliberate, restorable
mutation test — `lr`'s `vwmatrix` temporarily written to duplicate `ll`'s
`(2,1)` — made `/api/video_wall/detect` correctly report `status:
"conflict"` naming both decoders' IDs at `(2,1)`; `lr` was then restored to
its exact original `vwmatrix`/`vmenable` and a final detect call confirmed
`status: "complete"` again, with the pre- and post-values read back and
compared byte-for-byte. No firmware, factory reset, password, or network
change was made to any device at any point.

**Not performed in this pass** (explicitly deferred rather than rushed):
live-hardware writes for invalid/out-of-range coordinate, dimension
mismatch, and an alternate topology (1x2/2x1) scenario. The corresponding
*algorithm* behavior for all three is covered by synthetic tests in
`tests/test_video_wall_detection.py` (which also covers the duplicate-
coordinate and complete/partial/standalone/multiple-wall cases exercised
live above); only the live-device demonstration of those three specific
scenarios was deferred, to keep real-hardware mutation to the one
well-understood, fully-restored cycle described above.

### Persistence relationship

Detection never writes `video_walls.json`. A detected wall that matches an
existing saved wall (by rows/columns + decoder-ID set) is offered as "open
that saved wall"; one that doesn't match is offered as an unsaved,
in-memory candidate the operator can inspect, edit with the same spatial
UI as any other wall, and Save (or discard by navigating away) — the
existing save/apply/import/export model is otherwise completely
unchanged.

## 27. Video Wall: `StandardVideoWallInfo.Set` write behavior (verified live, 2026-09-18)

Four additional real-hardware scenarios were run against the same
four-decoder 2x2 (dimension mismatch, two alternate topologies, an
out-of-range coordinate), each captured, applied, read back, and restored
with a final "complete, 4/4" detection confirming restoration. Two
genuine device behaviors emerged that §26's detection algorithm already
handles correctly by construction, but which anyone calling
`StandardVideoWallInfo.Set` directly needs to know:

- **A `vwmatrix` write made in the same call as `vmenable: false -> true`
  is not reliable.** Observed twice: a decoder whose `vmenable` was
  `false` at the moment of the call had its `vwmatrix` request silently
  not applied — the Set() response echoed the requested value with
  `"ok": true`, but an immediate readback showed the coordinate
  unchanged. The same request against a decoder already at
  `vmenable: true` applied on the first try. **The reliable pattern is
  two separate calls: first `Set({vmenable: true, vwmatrix: <its current
  value>})` to prime it, then a second `Set({vmenable: true, vwmatrix:
  <the new value>})`.** `_vw_set_wall_info_if_needed()` (§14) does not
  currently do this priming — it is a single `if-needed` call — so a
  cell entering wall mode for the first time in the same operation that
  also changes its position could theoretically hit this. Not fixed
  here: no failure of this kind has been observed through LumaSuite's own
  UI paths in this pass (every write made through the app itself, via
  Save/Apply/drag-drop, applied correctly), and changing the idempotent
  write helper on unverified suspicion would be exactly the kind of
  unrequested speculative change AGENTS.md warns against. Documented as a
  known device characteristic to watch for if a future report describes
  a wall-mode entry not taking effect on the first attempt.
- **The device validates coordinate range but not cross-decoder
  consistency.** `vwmatrix="2_2_3_1"` (row 3 of a claimed 2x2) was
  **rejected outright** with JSON-RPC `-32602 Invalid params` — a real,
  explicit protocol-level validation error, not a silent no-op.
  `vwmatrix="3_3_2_2"` (internally valid — row/column 2 are within 1..3 —
  but inconsistent with the other three decoders' 2x2) was **accepted and
  applied** once the two-step write above was used. The device only
  bounds-checks a coordinate against its own claimed dimensions; it has
  no concept of "the other decoders in this wall" to cross-validate
  against, which is exactly why `_vw_detect_walls()` (§26) treats
  dimension agreement as something to *discover*, not something the
  hardware guarantees.
- **`vmenable` continued to change on its own outside of any write this
  session made**, consistent with §26's finding that it is not a stable
  membership signal: partway through this pass all four decoders were
  observed at `vmenable: true` (two had started at `false`) without a
  corresponding request from any script here. Topology (`vwmatrix`)
  showed no equivalent drift throughout — every topology read matched
  either the original baseline or the immediately preceding intentional
  write. This is the practical reason `_vw_detect_walls()` was designed,
  from the start, to never use `vmenable` for membership (§26) — it is
  reaffirmed, not newly discovered, by this pass.

### Test-by-test result

| Scenario | Mutation | Device response | Detector result | Restored |
|---|---|---|---|---|
| Dimension mismatch | `lr`: `2_2_2_2` → `3_3_2_2` | Applied (2-step write) | Two groups: 2x2 partial (3/4, missing R2C2), 3x3 partial (1/9) — never merged | Yes, verified |
| 1x2 alternate topology | `ul`→`1_2_1_1`, `ur`→`1_2_1_2` | Applied (2-step write) | 1x2 complete 2/2 (R1C1=ul, R1C2=ur); remaining ll/lr correctly reported as a separate partial 2x2 | Yes, verified |
| 2x1 alternate topology | `ll`→`2_1_1_1`, `lr`→`2_1_2_1` | Applied (2-step write) | 2x1 complete 2/2 (R1C1=ll, R2C1=lr); remaining ul/ur correctly reported as a separate partial 2x2 | Yes, verified |
| Invalid coordinate | `lr`: `vwmatrix="2_2_3_1"` | **Rejected**, `-32602 Invalid params` | N/A — device never held the invalid value | N/A — nothing to restore |

Final state after all four: fresh live reads of all four decoders
confirmed `vwmatrix` exactly matching the original baseline
(`ul=2_2_1_1, ur=2_2_1_2, ll=2_2_2_1, lr=2_2_2_2`), and

**Capability gate result: B** -- a small, generic backend extension (a
persisted `wall.zones` field) was added, but the underlying LumaStream
`StandardVideoWallInfo.Set`/`SelectVideoStream.Set` protocol and the
existing `wall.regions` model (§25) already supported arbitrary rectangular
sub-walls of any size/orientation; the 2x2-only restriction was entirely in
the frontend's crosshair hit-testing, not the backend or the protocol.
**Verified live** against the real four-decoder hardware, rearranged
through 1x2, 1x3 (whole span + a carved 1x2 sub-region), 1x4 (whole span +
an INTERIOR 2-cell sub-region touching neither edge), 2x1, 3x1 (whole +
sub-region), 4x1 (whole + interior sub-region), and a 3x3-partial wall
(found already configured on the hardware at the start of this pass --
`ul/ur/ll/lr` at `R1C1/R1C2/R2C1/R2C2` of a claimed 3x3 -- reused as a
live partial-larger-wall test: routing a source to just that populated 2x2
sub-rectangle correctly wrote the REGION-LOCAL `2_2_r_c` geometry to all
four decoders, not the wall's own `3_3_r_c`). Every scenario was restored
and the hardware finished at the exact known-good 2x2
(`ul=2_2_1_1, ur=2_2_1_2, ll=2_2_2_1, lr=2_2_2_2`, rotation
`180/180/0/0`), confirmed by a fresh `_vw_detect_walls()` call
(`complete`, 2x2, 4/4, correct mapping).

**The zone/region split -- the architecturally important decision.**
`wall.regions` (§25) continues to mean exactly what it always has: LIVE,
ACTIVE routing state, created by a single drag/drop or click-Route action,
resolved by `_vw_effective_matrix_and_source()`/`effectiveGeometryAndSource()`
ahead of a cell's own `source_mode`, and dissolved by "Apply to Entire
Wall" (`snapAllDisplaysToWallVideo()`/its backend equivalent). A NEW,
separate field, `wall.zones`, holds SAVED, REUSABLE rectangle
*definitions* an operator can route a source to later -- a different
lifecycle entirely: zones carry no `source_id`, trigger no device call by
existing, survive "Apply to Entire Wall" untouched, and (unlike regions)
MAY overlap each other ("Top Row", "Left 2x2" and "Entire Wall" can all be
saved on the same wall). Canonical shape is a rectangle's two corners
(`row1,column1,row2,column2`); member cells are always DERIVED from that
(`_vw_zone_cells()`/`zoneCellsOf()`), never stored twice. Backend:
`_vw_clean_zones()` (mirrors `_vw_clean_regions()`'s bounds/rectangle
checks but drops the overlap-exclusivity rule and the `source_id`/
`source_snapshot` fields), wired into `_vw_clean_wall()` exactly like
`regions` -- so save/load/import/export round-trip zones through the
existing pipeline with zero new endpoints. Routing to a saved zone is
client-driven: the frontend synthesizes an ordinary region over the zone's
cell set and posts it through the SAME `/api/video_wall/source
scope="region"` call a crosshair-drawn region always used -- one routing
engine, not two.

**2x2 convenience zones: computed, never persisted.** A 2x2 wall
auto-exposes four convenience targets (Top/Bottom/Left/Right, replacing the
old crosshair's four pair targets) via `autoZonesForWall()` -- generated
on the fly from the same generic rectangle engine every save load
recomputes them from, tagged `auto:true`, never written to
`video_walls.json`. This was the deliberate "smallest consistent model"
choice: no wall size gets special-cased storage, and a 2x2 wall's
convenience targets can never drift out of sync with its actual dimensions.
The old four-display "whole wall" target remains, as before, NOT a zone --
routing to it still reuses `wall.source_id`/"Apply to Entire Wall" exactly
as §25 describes; the zone rail's "Entire Wall" chip is a special,
non-zone rail entry for exactly this reason.

**The crosshair is fully retired.** `ui/wall.js`'s `positionCrosshair()`,
`crosshairZoneCells()`, `crosshairZoneForCells()`, the `crosshairDragging`
flag, and `ui/wall.html`'s `#wallCrosshair`/`.wall-cross-zone` markup and
CSS are gone (guarded by a regression test in
`tests/video_wall_model.test.js` that fails if any of those symbols
reappear). In its place: every multi-cell routing target (a saved zone, an
auto 2x2 convenience zone, or "Entire Wall") is its own always-visible,
individually-labeled chip in a new zone rail below the grid
(`renderZoneRail()`/`.zone-rail`/`.zone-chip`), each a real, separate
native HTML5 drop target -- so there is no overlapping/invisible hit-area
to disambiguate and no pointer stickiness (`hitTestTarget()` is now a pure
`elementFromPoint` -> `.wall-cell` lookup with no wall-size branching at
all). A non-drag path exists in parallel and calls the exact same
`assignSpatialTarget()` the drag/drop path calls: click a source tile to
arm it, click a display or a rail chip to choose the target, click Route
(`armSourceForNonDragRouting()`/`routeArmedSourceTo()`/`commitArmedRoute()`).

**Edit Zones mode.** A dedicated top-bar toggle (`#editZonesBtn`) enters a
mode where the Sources panel is replaced by a Zone Editor panel and source

## 32. Video Wall: site discovery -- existing-configuration candidates (added 2026-09-19)

Extends §26's read-only single-wall detection into a full site-discovery
feature: every eligible decoder's already-configured Video Wall state is
classified into qualitative candidates, surfaced as an unobtrusive Device
Manager notification and a compact Video Wall page section, and reviewed
through the existing Create/Edit Wall wizard component -- no second wall
renderer, no second scanner, and (this is the release-blocking property)
**zero device writes anywhere in the feature**, verified empirically
against real hardware, not just by code inspection (see "Zero-write proof"
below).

### Phase 1 -- real-hardware evidence investigation (done first, verified live)

Every plausible wall-membership signal was inventoried against the real
four-decoder 2x2 (`ul`/`ur`/`ll`/`lr`) before any grouping heuristic was
built:

| Signal | Source | Already collected in a normal scan? | Changes with routing? | Verdict |
|---|---|---|---|---|
| `vwmatrix` (rows/columns/row/column) | `StandardVideoWallInfo.Get` | No -- Video-Wall-specific, only read by `_vw_read_decoder` | Only when the operator explicitly re-routes/re-assigns (verified: unchanged across whole-wall routing, an individual override, and while a region was NOT touching that decoder) | **STRONG / AUTHORITATIVE** -- unchanged from §26 |
| Saved wall's exact decoder-ID set | `video_walls.json` | N/A (local file) | Never, except by an explicit Confirm & Save/Edit | **STRONG / AUTHORITATIVE** for "this is a previously confirmed wall" |
| `vmenable` | `StandardVideoWallInfo.Get` | No | Yes -- toggles with wall-mode vs. override, and was observed to drift on its own outside any write this pass made (reconfirms §27) | **PROHIBITED ALONE** -- unchanged from §26 |
| `streamname` / current source | `SelectVideoStream.Get` | No (Video-Wall-specific call; a normal scan's `_query_decoder_details` reads decoder audio/video stream info but never `StandardVideoWallInfo`/`VideoWallBezel`/`VideoWallDisplayPref`) | Yes -- highly volatile, verified again this pass (individual override and region routing each changed it independently per decoder while topology stayed put) | **SUPPORTING ONLY** -- shown per-cell, never allowed to split or merge a group |
| `VideoWallBezel.Get` ("crop"/geometry) | `VideoWallBezel.Get` | No | **No** -- see below | **UNUSABLE**, newly determined this pass |
| `VideoWallDisplayPref.Get` (`rotate`) | `VideoWallDisplayPref.Get` | No | No -- stable per decoder throughout | Informational only (physical mounting, not topology); never evidence |
| Discovery order / IP ordering / hostname similarity | -- | -- | -- | **PROHIBITED**, always was |

**Real-hardware crop/bezel investigation (the specifically-requested
check) -- crop is NOT usable evidence.** `VideoWallBezel.Get` was read on
all four real decoders in four states: the original whole-wall 2x2, an
individual 1x1 override (one decoder routed to a different source outside
wall mode), an active 2-cell region (top row routed to a third source),
and after restoring to whole-wall. In every single state, all four
decoders reported the byte-for-byte **identical** bezel:
`{totalwidth:1000, totalheight:564, topborder:8, bottomborder:8,
leftborder:8, rightborder:8}` -- regardless of which quadrant (R1C1
through R2C2) the decoder occupied, and unchanged by routing mode or
source. This directly disproves the plausible-sounding hypothesis that
four decoders in a real 2x2 would report complementary per-quadrant crop
rectangles: they report the same value because it describes each
decoder's own physical display + bezel compensation (an installer-entered
constant, coincidentally identical here because the four screens are the
same model), not a wall-position-derived crop. Bezel/crop carries **no**
topology signal and is excluded from the evidence hierarchy entirely --
not weakened to "weak", genuinely unusable.

**Real-hardware common/current-stream investigation.** Confirmed
independently in three separate live tests this pass (individual
override, region routing, and a temporary dimension-mismatch/partial
scenario): `streamname` changes per-decoder based purely on the most
recent routing action and is never uniform in a way that would help
disambiguate membership, reconfirming (not merely repeating) §26's
finding under the new candidate pipeline. It is surfaced in the Review
dialog's "Why?" panel as explicitly supporting-only context and is never
read by `_vw_classify_candidates()`'s status logic at all.

### Evidence hierarchy (implemented in `_vw_classify_candidates` et al., `lumaserver.py`)

- **Strong / authoritative**: `vwmatrix` (rows/columns/row/column); a saved
  wall's exact decoder-ID set (regardless of current coordinates).
- **Supporting only** (shown to the operator, never allowed to establish,
  split, or merge membership by itself): `streamname`/current source;
  rotation (physical mounting, informational).
- **Explicitly prohibited from establishing membership alone**: discovery
  order, IP ordering, hostname similarity, `streamname` alone, `vmenable`
  alone.
- **Unusable** (real-hardware finding, not assumption): `VideoWallBezel`
  crop/geometry.

### Candidate model, identity, and statuses

`_vw_run_detect()` (the only function in this feature that talks to a
device -- one parallel round of the exact same `.Get` calls
`_vw_read_decoder`/§26 already made) feeds `_vw_detect_walls()`'s existing
groups into `_vw_classify_candidates()`, which is pure and does no I/O.
Each candidate gets:

- **`fingerprint`** -- a stable identity derived from `(rows, columns,
  status, sorted {position: device_id} pairs, sorted conflict claimants)`,
  hashed (sha1, truncated). Independent of discovery order (the member map
  is sorted first); sensitive to any material change (a member moving,
  appearing, disappearing, or the status itself changing). This is what
  Ignore keys off, and what makes "an unchanged rescan doesn't re-nag, a
  materially-changed candidate does" a content-derived property rather
  than a heuristic.
- **`device_set_fingerprint`** -- `(rows, columns, sorted device-ID set)`
  only, position-independent. Used for saved-wall matching (the same rule
  §26's `matched_saved_wall` always used) and stored on a newly confirmed
  wall as `confirmed_fingerprint`.
- **`candidate_status`**, one of five qualitative labels, never a numeric
  confidence score anywhere in the model or the UI:
  - **DETECTED** -- matches an existing saved wall's exact decoder set,
    and live state has not materially diverged from what was saved.
  - **POSSIBLE** -- a complete, non-conflicting group with no saved match
    (a fresh, unconfirmed candidate).
  - **PARTIAL** -- some coordinates unclaimed; the missing coordinates are
    named honestly, never guessed.
  - **CONFLICT** -- one or a few coordinates double-claimed, consistent
    with an ordinary misconfiguration.
  - **AMBIGUOUS** -- a conflict where the total claimant count and the
    fraction of contested coordinates both look like two or more
    same-size walls overlapping in coordinate space rather than one
    misconfigured wall (heuristic: total claimants >= 2x the wall's cell
    count AND at least half its coordinates are contested). Presented
    honestly ("N decoders contain RxC configuration; LumaSuite cannot
    reliably determine which decoders belong to each physical wall of
    this size") with a pointer to the manual decoder-assignment path
    (Create/Edit Wall), never a guessed split. **Simulated only** -- the
    real test rig has four decoders, and this scenario needs at least
    eight to construct two genuine same-size walls; covered by
    `tests/test_video_wall_candidates.py`.
- **`known_wall_changed`** -- set (independent of the five statuses above)
  when a candidate matches a saved wall by device-ID set but its live
  positions/dimensions/completeness have materially diverged since that
  wall was confirmed; carries a plain-language diff (`"<device>: moved
  from R1 C1 to R1 C2"`, `"<device>: no longer detected..."`, `"Now
  incomplete: missing..."`) rather than silently rewriting the saved
  definition. Verified live: swapping `ul`/`ur`'s `vwmatrix` against the
  real hardware produced exactly this diff, and restoring them made the
  wall DETECTED again on the next read.
- **`ignored`** / **`needs_review`** -- see dismissal lifecycle below.

**Verified empirically, not just by inspection**, against the real

### An important, real-hardware-verified interaction: active regions and detection

A region is not just UI state -- routing one genuinely rewrites the
affected decoders' `vwmatrix` to the region's own **local** geometry (§25).
Verified live: with the real wall's top row (`ul`+`ur`) routed to a region
source, a detect pass correctly split the wall into a **1x2 DETECTED**
candidate (matching a previously-saved "1x2 top" sub-wall exactly) and a
**2x2 PARTIAL** candidate (2/4, the remaining `ll`/`lr`) -- an accurate
reflection of what the hardware was actually reporting at that instant,
not a bug. This is the correct behavior, not a case needing suppression:
detection must describe live device state honestly, and a region is a
legitimate (if transient) topology change as far as the protocol is
concerned. The saved 2x2 wall's own `regions`/`zones` fields were
confirmed completely unaffected by this (`regions: []`, its pre-existing
saved `zones` unchanged) -- the live region never touched saved
zone/region definitions in either direction.

### Efficiency

A short-TTL (15s) in-process cache (`_VW_DETECT_CACHE`/`_vw_cached_detect()`)
is shared by `/api/video_wall/detect` and the new
`/api/video_wall/candidates_summary`, invalidated immediately by any call
that changes device wall state (`save`/`delete`/`import`/`/source`/`/apply`)
via `_vw_invalidate_detect_cache()`. This means opening Device Manager and

## 33. Hall Research published-firmware status (added 2026-09-19, release-audit addendum)

**VERIFIED FROM SOURCE + REAL HALL RESEARCH WEBSITE + REAL HARDWARE.** Added
during the release-readiness audit after operator acceptance flagged that a
device's installed firmware version had no automatic comparison against
what Hall Research has publicly published -- the operator had no way to
know "is this current" without leaving the app. This is CHECK + COMPARE +
DISPLAY only; it never installs firmware and never touches the existing
explicit upload/upgrade flow (`POST /api/upgrade`).

### This is a second, independent question from the existing "Check Firmware" button

*(Renamed to "Check Local Firmware Files" in the 2026-09-19
release-preparation pass, §34, precisely to make this distinction explicit
in the UI itself -- label/tooltip only, see §34 for what did and didn't
change.)*

Investigation (reading `ui/index.html`'s `checkFirmwareSelected()` and
`lumaserver.py`'s `api_firmware_check()`, §13) confirmed the existing
Device Manager **Check Firmware** button answers a *different* question:
"does the operator already have a newer firmware file sitting in their
local `firmware/` folder than what's on the device." It has never
contacted the internet and never will -- it's a local-file comparison, and
was NOT removed or changed, despite the initial framing of this addendum
assuming it was the manual version of the new automatic feature. Both
features coexist, are visually distinct badges in the same Version cell,
and answer different operator questions:
- **Check Firmware** (button, manual, unchanged): installed vs. locally
  downloaded `.tar.gz` files.
- **Hall firmware status** (new, automatic, this section): installed vs.
  Hall Research's public release for that product family.

### Authoritative public source

`https://hallresearch.com/product/<slug>#firmware` is a client-rendered
shell (confirmed live: the raw page loads as `Loading product...` with a
557-character body) -- there is no static/server-rendered HTML source to
scrape. Network inspection of the rendered page (real headless-browser
load, request log captured) shows it fetches its own content from Hall's
first-party, same-origin, unauthenticated JSON API:

```
GET https://hallresearch.com/api/products/<slug>
```

This is the source used here -- not scraped visible text, not a
third-party firmware database, not a search engine result. Response is
Prismic CMS content resolved to JSON; the only fields read are
`data.firmware[].version[].text` (plain version string once its rich-text
paragraph blocks are concatenated, e.g. `"1.0.2"`) and
`data.firmware[].release_date` (`"YYYY-MM-DD"` or `null`). Multiple
firmware entries can exist (confirmed live for CS31, which lists two); the
highest by parsed version tuple is used, never the first array element.
`data.firmware[].firmware_link.url` is **never read** -- this feature
never treats a Hall-supplied URL as an install source, and never becomes
part of the existing official-release-URL validation path used by the real
upload flow.

2026-09-19):

|---|---|

Matched by case-insensitive **prefix**, not exact string or substring, so

### Version comparison

Reuses the existing `_parse_full_version_tuple()` (already used by the
local-file Check Firmware feature, §13) unchanged -- both an optional
leading `V`/`v` and an arbitrary number of dot-separated integer
components are handled the same way for installed and published strings.
Comparison is a plain Python tuple compare of integers (never a string/
lexicographic compare), so `1.0.10 > 1.0.2` compares correctly. Rule:
`installed_tuple >= published_tuple` -> **Up to Date**; otherwise ->
**Update Available**. The `>=` (not `==`) is intentional: a development/
engineering unit legitimately running ahead of Hall's current public
release must never be reported as needing an update or downgrade.

### No-internet / unavailable behavior -- no badge, ever

If a product's publish lookup fails for any reason (DNS failure, timeout,
non-200, malformed JSON, missing `firmware` section, oversized response) or
a device's model doesn't map to a known product, that device's Version
cell shows **only the installed version**, exactly as it did before this
feature existed -- no "Unknown" badge, no warning, no toast, no console-
visible-to-the-operator error. `Unknown` is reserved for the existing,
unrelated case where the *installed* version itself can't be determined
locally (`api_firmware_check`'s own `unable_to_check` state) -- never used
to mean "internet enrichment failed."

### Startup / caching / failure isolation

No module-level or `__main__`-only startup hook. `GET
/api/firmware_status` lazily starts exactly one background daemon thread
the first time it's ever called in the process's lifetime
(`_ensure_hall_firmware_lookup_started()`, guarded by
`_hall_firmware_fetch_started` under `_hall_firmware_lock`); every
subsequent call to the route, however many, reuses the in-memory result
without issuing another Hall request. This is 3 fixed Hall requests total
per process lifetime (one per known product, not per discovered device,
not per scan, not per row) with short bounded timeouts (`(3, 5)` seconds
connect/read each). The route itself never blocks on the network -- it
returns immediately with whatever is already cached (verified: a request
with a Hall response mocked to take 1.5s still returns in well under 1s).
The frontend (`ui/index.html`, `refreshHallFirmwareStatus()`) calls this
once after initial load and once after each Scan (both cheap, in-memory,
zero additional Hall traffic), plus up to 3 bounded 4-second-spaced retries
if the background fetch was still `"pending"` on the first call, handling
a Hall result arriving after the initial device rows already rendered
without requiring the operator to do anything. Cache is in-memory only,
cleared on process restart -- no persisted "current published version" is
shipped or hard-coded anywhere in source; every lookup re-fetches from
Hall.

### Security

HTTPS, fixed Hall-owned domain hard-coded in source (never derived from
device or user input), no credentials sent or received, response size
capped (`HALL_FIRMWARE_MAX_RESPONSE_BYTES`, 5 MB) before JSON parsing, all
failure modes caught and isolated per-product so one product's failure
never blocks the others or the caller.

## 35. Video Wall: routing-target order + post-route preview-refresh burst (added 2026-09-19)

Two narrow, independent UX fixes to the Video Wall's live-preview/routing
experience, made after an explicit investigate-before-implementing pass.
Neither changes routing semantics, target ids, zone definitions,
existing-site detection, or the two-step `vmenable`/`vwmatrix` write
sequence (§27).

**1. "Entire Wall" is now the first routing target.** `ui/wall.js`'s zone
rail previously appended saved zones, then the 2x2 auto convenience zones
(Top/Bottom/Left/Right), then "Entire Wall" last. The ordering logic was
pulled out of `renderZoneRail()` into a new pure function,
`zoneRailTargets(wall)`, which returns targets in the order Entire Wall ->
2x2 auto zones -> operator-saved zones, and is exercised directly by
`tests/video_wall_model.test.js` without needing a DOM. This is
presentation order only: `zonesForRouting()` (still used unordered, for
hit-testing/label lookup in `zoneForCells()`) and every target's id/cell
membership/click-routing behavior (`wireRailTarget()` calling the same
`assignSpatialTarget()`/`routeArmedSourceTo()` path) are unchanged.
Verified live in a headless browser against the real four-decoder 2x2
(§26's saved wall) at 1280x720 and 1440x900, Light/Dark x Classic/Compact
(8 combinations): "Entire Wall" first in every case, zero console errors,
zero failed requests, zero horizontal overflow.

**2. Root cause of the reported ~10s "preview feels stale after routing"
complaint: LumaSuite's own preview-refresh scheduling, not the decoder.**
Direct real-hardware measurement (bypassing the UI: `SelectVideoStream.Set`
issued directly against `ul`, alternating between two distinct encoder
streams, polling `http://<ip>/thumbnail/thumbnail1.jpg` with a fresh
cache-busting query param each attempt until the JPEG's content hash
changed) found the decoder's own route-accept-to-new-thumbnail latency is
consistently under ~1.6 seconds (four trials: 0.086s, 0.161s, 0.482s,
1.594s), nowhere near 10 seconds. The actual cause was that
`liveRouteSource()`/`liveRouteRegion()` triggered no preview refresh of
their own after a successful route -- the browser's next fetch of a
routed cell's thumbnail was whatever the *independent*, already-running
periodic timer (`scheduleWallPreviewRefresh()`, `wallPreviewRefreshSeconds`,
default 10s, operator-adjustable 2-10s) happened to do next, which in the
worst case (a route landing right after a periodic tick) meant waiting
nearly a full period for the UI to even ask the decoder for a new image.
Browser caching was investigated and ruled out as a contributor: every
periodic and burst refresh already built its request URL via the
pre-existing `previewUrlWithCacheBuster()` (`?t=<timestamp>`), so the
browser was never serving a stale cached response for an intentional
refresh -- the delay was entirely about *when* a refresh was attempted,
not what happened once one was.

**The fix: a short, self-terminating post-route "burst," scoped to only
the cells that route actually touched.** `refreshWallPreviewImages()`
gained an optional `cellKeys` filter (a `Set` of `"row:column"` strings;
omitted, it behaves exactly as before -- every visible preview, the
periodic timer's existing call site). A new `burstRefreshPreviewsForCells
(cells)` fetches those cells' previews immediately, then again at +700ms,
+1500ms, +3000ms (`PREVIEW_BURST_DELAYS_MS`), then stops -- a fixed,
finite list, not a poll loop; a `previewBurstSeq` token means a new route
started before a prior burst finishes supersedes it rather than the two
overlapping. `liveRouteSource()` and `liveRouteRegion()` each call it,
unawaited, with the exact `targets` array that call already routed --
covering single-display, zone, and Entire Wall (which routes via
`liveRouteSource("wall")`) the same way. The route's own device calls
(`/api/video_wall/source`, `saveWallQuiet()`) complete and their
success/failure toast fires before the burst is even started; the burst
performs zero `api(...)` calls and thus zero device `.Set` traffic --
verified both by direct source-text inspection and by
`tests/video_wall_preview_refresh.test.js`, which loads the real
`ui/wall.js` into a `vm` sandbox with a synthetic DOM/`Image`/timer surface
and asserts: the burst only ever touches the routed cell(s)' preview
elements (an unrelated cell's `style.backgroundImage` is never set), it
performs exactly one attempt per configured delay and then stops
scheduling further timers, a new route's burst supersedes a still-running
previous one, cache-busting values differ across attempts, and a disabled
preview toggle makes it a complete no-op. With the burst's delays chosen
to comfortably straddle the measured worst-case decoder latency (1.594s),
the realistic post-fix delay is the first burst attempt that lands after
the decoder's thumbnail actually changes -- typically the immediate or
+700ms attempt, worst case (given the range measured) the +1500ms or
+3000ms attempt -- rather than up to a full periodic-timer period.

**Real hardware used**: the four development decoders (`ul`=198.51.100.51,
`ur`=198.51.100.68, `ll`=203.0.113.53, `lr`=198.51.100.54) and two
encoders (203.0.113.43 `room-a`, 203.0.113.42 `LUMA-E4-TEST02`).
**Pre-existing hardware finding, unrelated to this pass**: at the start of
this pass the four decoders' live `vwmatrix` was already `2_1_1_1`
(`ul`/`ur`, a genuine duplicate-coordinate conflict) / `2_1_2_1`
(`ll`/`lr`, likewise) -- a 2x1-shaped conflict, not the 2x2 baseline
recorded in §26/§27/§31, with `streamname` uniformly `room-a` on all

`_vw_detect_walls()` read), is exactly what the existing, unmodified §26/

## 36. Remote Access, accounts, display groups and the verified route (v1.1.0)

**VERIFIED FROM SOURCE AND TESTS.** Adapted from the consolidated OmniSuite architecture; LumaStream
protocol behaviour is unchanged and remains authoritative.

**Modules** (all at the repository root, imported by `lumaserver.py`, wired in `luma_wiring.py`):

| Module | Owns |
|---|---|
| `luma_access` | Every route's class (`PUBLIC`, `AUTHENTICATED`, `USER`, `ADMIN`, `LOCAL_ONLY`); unknown route is denied; `/ui/<file>` is classified per file from an allowlist |
| `luma_gate` | One `before_request` check: local listener, remote-enabled, session, CSRF, link-session barrier, role, then per-source / per-display / per-group permission |
| `luma_remote` | The optional second listener, and the tag every listener stamps on a request |
| `luma_users` | Accounts, scrypt hashes, throttling, sessions, Direct Access, audit; `Permissions` = sources, displays, groups |
| `luma_tls`, `luma_adapters` | Certificates (SAN-only validity, key mode 0600) and adapter identity |
| `luma_projection` | The restricted User view, built from named fields |
| `luma_groups` | Display Groups store and the sequential runner |
| `luma_aliases` | Friendly names, keyed by MAC; presentation only |
| `luma_locks`, `luma_statecache` | Per-display locks (sorted, bounded wait) and single-flight observation |
| `luma_store` | Atomic, serialized JSON writes, read-modify-write under one lock, quarantine of malformed files |
| `luma_backup` | Encrypted backup container, sections, restore snapshot/rollback |
| `luma_destinations` | Where a remote caller may make the server connect: a known device for control, a non-public address for discovery |
| `luma_audit_text` | Activity sentences; an unknown event or reason falls back to English, never to its id |
| `luma_remote_api`, `luma_wiring` | The HTTP surface and the assembly |

**Trust.** Whether a request is local is a fact about the *listener that accepted it* (`luma.listener` in the WSGI
environ, set by `luma_remote.serve_tagged`), never a header or the peer address. The application's own listener
binds loopback by default (`LUMA_HOST` overrides; a non-loopback bind is tagged remote and gated). Both entry points
(`python lumaserver.py`, `app_launcher.py`) must create their server through `serve_tagged`; a test fails otherwise.

**Identity.** Permissions, aliases and groups use a canonical MAC (`luma_projection.canonical_identity`); an address
is rejected, never converted. A unit with no MAC has no identity and is never assignable. The existing IP-keyed
transport is unchanged: identity resolves to the current address, then the existing engine is used.

**Routing.** `lumaserver._route_av` is the one verified route: it reads the encoder's stream live, writes the
decoder, reads the decoder back (3 reads), and only then updates the cache -- from the device's answer. Admin
`POST /api/route_matrix` is a thin wrapper (it keeps its cached-stream fallback); User routes never use a cached
stream. **Audio and video are one route**: LumaStream routes by selecting the encoder's stream on the decoder, and
the decoder's audio follows when `SelectAudioStream.followvideoenable` is on. A restricted User's A/V
(`_route_av_for_users`, behind Standard routing, a drop and the User Matrix alike) goes through the breakaway
engine as `MODE_USER_AV`: a following display gets one video write and keeps following; a display left not following
(after a breakaway) gets the source's audio written explicitly, audio first, and both planes are read back; a source
with no audio stream is refused by the engine before any write and routed by `_route_av` as video, reporting
`not_following` where it applies. The result reports `follows` / `routed` / `not_following` / `unknown`. `user_av`
is not in `MODES`, so the administrator's endpoint cannot name it. Every multi-destination route
(Standard multi-select, Display Group, saved Video Wall, Matrix row) is **one engine**, `luma_remote_api._run_batch`:
(1) authorise the whole request and resolve groups and walls to member decoders on the server, (2) answer a wall that
cannot be routed at all (source offline or silent) without writing, (3) prepare one operation per decoder, (4) dispatch
them in one bounded parallel batch (`luma_groups.run_parallel`, `DISPATCH_WORKERS` = 6, clamped 1-8, `LUMA_ROUTE_WORKERS`
overrides), (5) each operation locks its own display only (never two at once, so parallel dispatch cannot deadlock),
re-checks the account before the wait and on the far side of it, routes and reads back, (6) aggregate. A failure never
stops the rest and nothing is rolled back. Worker threads get a copy of the request context so authorisation reads the
live session. The response carries `timing` (ms since the batch began: first/last write-operation start and end,
`start_spread_ms`, `workers`) and nothing else about the devices; `tools/measure_route_spread.py` measures it against a
running app, `python tests/test_route_parallel.py --measure` against the stub.

**Saved wall in the User Matrix.** The wall row offers A/V, Video and Audio. The wall grant is the only authority; the
members are resolved on the server at route time (`_WallPlan`) and are never named by the request. Per member (followed
cells only; own-source and region cells are left alone and counted): A/V = the wall's own cell operation (stream +
wall matrix) then the User A/V engine (both planes, read back); Video = the breakaway engine's video-only mode first
(it pins that member's audio) then the cell operation; Audio = the breakaway engine's audio-only mode only (video and
wall settings untouched). The wall row answers `verified`, `partial` or the first failure; the saved wall's source is
updated only when the picture changed and every member verified.

**Audio follows video (Standard Routing).** A routing preference, not a permission: `audio_follows_video` (boolean,
default true, anything else is 400 `bad_preference`) is read only for the Standard interface. True = the User A/V route
(both planes); false = the video-only engine mode (audio preserved), for displays, groups and walls alike. The Matrix
ignores it. The page keeps it in memory only (on for every new page load): no grant, no server copy, no browser storage.

**Matrix preview.** The hover preview is on the routing cell (dot) of the User Matrix, one frame per hover, debounced,
cancelled on leave, dropped on close; the source heading alone is not a trigger.

**Previews.** Server-fetched, by identity, after authorization: display = `/thumbnail/thumbnail1.jpg`; source = the
live `/stream?...` view (the mechanism LumaSuite's own pages use), first JPEG frame, size- and time-bounded, cached
5 s single-flight. `LUMA_ENCODER_PREVIEW=thumbnail|auto` selects the encoder's `thumbnail1.jpg`, **not verified on
hardware**. No device "thumbnail enabled" flag is read.

**Persistence.** Runtime files added under the data folder: `users.json`, `security_audit.json`,
`device_aliases.json`, `display_groups.json`, `remote_access.json`, `remote_cert.pem`, `remote_key.pem`,
`restore-snapshot/`. All are git-ignored. `producer_config.json` (device passwords, plaintext as before) is now
written atomically and narrowed to its owner.

**Tests.** `tests/_fence.py` (installed by `tests/__init__.py` and `tests/_support.py`) blocks every non-loopback
socket, and pre-seeds the scratch data folder because an unseeded one would have `lumaserver` migrate the developer's
real runtime files into it. `tests/mutate_security.py` breaks each security predicate on purpose and requires the named
tests to fail; a survivor is a test gap, a badly aimed mutation, or a redundant control, and is investigated.
Always validate on the pinned stack (`requirements-build-lock.txt`, Python 3.12). Account hashes are Werkzeug's scrypt, requested
explicitly in `luma_users`; hashes written on Werkzeug 2.3.8 verify on 3.1.9 (checked against a data folder written by the old stack).

**Running the checks.** `python run_tests.py` runs every suite (one process each) and totals the results.
`python tests/mutate_security.py` is the mutation harness (`--check` verifies anchors only). A built artifact is
checked with `python tests/smoke_packaged.py <exe>` (pages, assets, listener tagging) and
`python tests/smoke_remote_packaged.py <exe>` (bootstrap, certificate, HTTPS, sign-in, CSRF, roles). Neither smoke
script is part of unittest discovery or CI.

**Open hardware validation.** Encoder `thumbnail1.jpg`; decoder thumbnail availability on every model; whether each
display's audio follows video after a route; CS31 as a display target (treated as one; preview via `/stream`).

## Product unification pass

What changed and why, for the next person. Operator-facing wording is in `ui/manual.html`.

**New modules.** `luma_scanplan` counts a scan expression arithmetically before anything is expanded (limits: 4096
addresses per range, 8192 per scan, 32 ranges; refused, never truncated). `luma_retention` holds the Activity
retention rules as pure functions (default 30 days and 4 MiB, bounds 1-365 days and 256 KiB-64 MiB, a hard 100,000
entry ceiling; the 4 MiB default comes from a measured 200-250 byte compact entry, about 330 bytes on disk).
`luma_breakaway` is the Admin audio/video routing transaction, with the device calls injected.

**Routed scanning.** There was no backend regression: `_expand_targets` is unchanged since v1.0.0 and the page's
scan code is identical to v1.0.8. What was missing was an *additive* second input: the Targets box REPLACED the
adapter (`text || chosen`) and was never remembered, so scanning a routed network meant retyping it every launch and
giving up the local network. The page now scans the adapter network plus "Additional networks (routed)", and the
server remembers them (`scan_ranges` in `producer_config.json`, validated on write and on load).

**Breakaway protocol (measured on real decoders).** `SelectVideoStream.Set {selecttype, streamname, password}`;
`SelectAudioStream.Set {followvideoenable, selecttype, streamname}`; reads by `.Get`; the decoder's valid audio names
from `AudioStreamNameList.Get`; an encoder's own names from `VideoMultiIpStream.Get` / `AudioMultiIpStream.Get`.
With follow off, a video Set never touches audio; turning follow on resyncs audio to the current video's encoder and
IGNORES the name sent, so "return to follow" is one audio write. The device accepts an audio name it does not have
and subscribes to `0.0.0.0:0`, so the name is validated against the decoder's list first and the read-back must show
a real address. Audio and video names may differ for one encoder (video `room-a`, audio `room-a1`). Switchers
(CS31) have no observed audio method and are offered AV only. `POST /api/route_matrix` with no `mode` is the
unchanged ordinary route; with a `mode` (`av`, `video`, `audio`, `breakaway`) it is `luma_breakaway.route`. The User
endpoints do not read a mode at all.

**Firmware status.** `/api/firmware_status` is fed by one daemon thread (`hall-firmware`) started by
`start_firmware_checks()` from both entry points, never at import: a check at launch, then every 7 days, or after 6
hours if a check found nothing. The last good answer per product is persisted (`firmware_status.json`, atomic,
validated on load) and survives an offline start; `stale` marks an answer that could not be refreshed. States:
`up_to_date`, `update_available`, `unknown` (with a reason) -- never "N/A" for a mapped model.

**HTTP default.** `last_choice()` reports `http` for a never-configured system and the Settings page offers it first.
The API still treats an omitted transport as HTTPS (omission is not consent), and plain HTTP still requires
`accept_insecure` in the request. A preference stored without a transport reads as HTTPS.

**Hostname certificates (investigated, not adopted).** The host's own name resolves on the host, but a single-label
name reaches only clients on the same segment (LLMNR/NetBIOS) and `<name>.local` is link-local multicast, which is not
forwarded between networks -- exactly the routed networks this product scans. A certificate naming a hostname that
some clients cannot resolve is worse than an address that always works, so HTTP stays the default and an
address-based certificate stays optional; a certificate the operator supplies may carry any name.

**Adapter ranking** is one function (`luma_adapters.rank_key`): connected before disconnected, usable address before
none, then wired Ethernet, Wi-Fi, other physical, virtual/VPN. It orders lists and picks a default only; a saved
selection is never re-ranked.

**Knowingly retired controls.** (1) *Check Local Firmware Files* (Device Manager): firmware availability is the
automatic check above; picking a file to upgrade is unchanged, and `POST /api/firmware_check` remains served (it is
classified and tested) but has no button. (2) The once-per-browser-session "Clear Units for optimal performance"
prompt: it interrupted use and covered Settings; the *Clear Units* button, its confirmation and its account/group
protection are unchanged.

**Packaged-acceptance fixes (2026-11-03).** (1) The shared Matrix refresh reads a CS31 switcher through
`_ws_call_switcher_no_password("SelectVideoStream.Get")` -- one read per refresh; a reply carrying an object `result`
is an answer even with an empty stream name (idle), and a stream name is recorded only when non-empty. Other unit types
are unchanged. (2) `luma_users.credential_fingerprints` records, per account, the fields in `_SECURITY_FIELDS`
(password, role, enabled, direct link, sources, destinations, groups, walls, standard and matrix routing);
`revoke_sessions_outdated_by` ends every session (password and link, administrator and user) of an account for which any
of them differs, or which is gone or disabled. The restore's "replaced accounts" list (`luma_backup._account_sig`)
already named role and permission differences, and its wording now says who is signed out. Nothing in the request can
keep a session; the restored account is also judged live on every request. (3) `accept_insecure` must be the JSON
boolean `true`. (4) `ui/user.js` fetches pictures through `pictureSlot` (at most `PICTURE_MAX` = 3 in flight, FIFO, a
route's picture promoted to the front); `stopPictureWork` (hidden, pagehide, sign-out, Preview off) drops what has not
started. (5) `/api/user/route_multi` and `/api/user/route_group` rows carry `reason` and `message` for a display the
engine declined with a known reason (`audio_not_available`), never the engine's own text. Known and left open:
a restore whose rollback meets a read-only data file reports the wrong status, and there is no single-instance lock.

## 37. Local application port: automatic by default, fixed on request (LUMA-MA-010)

**The two listeners.** LumaSuite opens two independent listeners, and MA-010 concerns only the first.

| | Local application listener | Remote Access listener |
|---|---|---|
| Started by | `app_launcher.py` (`AppWindow.run_server` -> `luma_portcontrol.PortController`) | `luma_wiring.RemoteAccess.restore` (`luma_remote.RemoteListener`) |
| Bound to | `127.0.0.1` | the adapter address the administrator chose |
| Port | automatic from 8090, or the fixed port (this section) | its own saved port, or `lumaserver.PORT` |
| Failure | the launcher shows the recovery state (below) | never prevents the local application from starting |

The new setting never reads or writes Remote Access's port, adapter, transport, certificate, sessions or URL generation; `luma_remote.py`, `luma_wiring.py`, `luma_tls.py` and `luma_remote_api.py` do not mention it (tested). `python lumaserver.py` has its own probe-forward loop and is left unchanged; it registers no controller, so the Settings block answers "not available in this run".

**What the launcher did before.** The default port (8090) was a CLI default; `find_available_port` probed forward at construction and the retry loop in `run_server` incremented the port on a bind error. That retry loop was effectively dead: werkzeug's `make_server` reports a failed bind with `sys.exit(1)`, not `OSError`, so only the pre-probe ever moved the port. The controller catches both `OSError` and `SystemExit` as "in use", and on Windows treats `10013` (how a bind refused by another listener's hold is reported) the same way.

**Modes** (`local_port.json`, additive, in the data folder): `local_port_mode` = `automatic` (default) | `fixed`, `configured_local_fixed_port` = 1024-65535. There are no product port reservations: whether a port is free is the bind's answer.

- *Automatic*: exactly the old behaviour (probe forward from 8090 up to 100 ports; a failed bind takes the next). Persists nothing.
- *Fixed*: binds exactly the configured port. A busy port is **never drifted away from**; the launcher shows the recovery state.
- A temporary alternate is session-only. The file is written only by Save and Restart, Make N Fixed, Change Fixed Port (after a successful bind), and Return to automatic.

**No configuration can prevent a start.** `PortSettings.load` never raises: missing, empty, whitespace, non-JSON, binary, non-object, unknown mode, wrong-typed or out-of-range port, fixed-without-port, or an unreadable path is quarantined (`luma_store.quarantine`, `local_port.json.corrupt`) and read as automatic. Writes use `luma_store.atomic_write_json` (unique temp file, fsync, `os.replace`, one lock per file). Extra unknown keys are ignored. A UTF-8 byte-order mark is tolerated.

**The bind is authoritative; the preflight is advisory.** `probe_bind` (a plain bind, as automatic discovery always did) is used to skip busy ports in automatic mode, to pre-fill the launcher dialog, and to refuse Save and Restart for a port that is plainly taken. It never gates the real start: a port that passes it and is taken before the bind recovers through the same recovery state (test 23), and one that looks busy but binds is used.

**Launcher recovery state.** Fixed port busy -> the launcher stays open: status `Server could not start`, `Configured TCP port N is already in use.`, buttons `Retry N`, `Start on Alternate Port`, `Change Fixed Port`, `Exit`. Retry binds the configured port (no config change). Start on Alternate Port uses the same free-port discovery as automatic mode, starts the complete server, shows the real URL and `Temporary port (configured: N)`, and writes nothing. Change Fixed Port is a Toplevel (`Change fixed TCP port` / `Configured port N is unavailable.` / `New TCP port:` / Cancel, Start): validate -> start on the new port -> **only then** save; failure keeps the saved bytes and the dialog open. Exit leaves without touching configuration (no native prompt, nothing is running). Normal startup is unchanged (same window, auto-opens the browser). Work runs off the Tk thread and results reach it through one queue (`AppWindow._post`/`_pump`). Operations are single-flight (`PortController._op`).

**Settings (local computer only).** `ui/port_settings.js` builds *Local Application Port* above Remote Access (it is a different listener and is not part of that section). Endpoints, all `LOCAL_ONLY` in `luma_access.ROUTES` (a remote session, including an administrator, gets 404; the handler checks again): `GET /api/local_port`, `POST /api/local_port/<action>` with `retry`, `make_fixed`, `change {port}`, `enable {port}` (Save and Restart), `disable`. Without a launcher (`luma_portcontrol.registered()` is None) the answers say "not available in this run". The block reads who it is from the session answer the page already has, so a remote administrator is never sent to a request that can only be refused. The dialog pre-fills the port **actually bound**, never 8090 (`dialogs.js` gained optional `field.value` and `field.help`).

**The launcher window follows the controller.** `PortController` keeps observers (`add_observer` / `remove_observer`) and calls them after every operation (alternate, retry, change, make fixed, disable, startup; the settings endpoints use the same methods), after `stop()` and after a failed-restart restore. An observer must not block and a raising one is logged and ignored. `AppWindow._on_controller_change` only queues onto the launcher's own UI queue (never touches Tk from the calling thread); on the Tk thread `_sync_from_controller` re-reads `ctl.view()` (the single derivation of port, URL, temporary, configured port) and `_render_running` draws URL, status, note and the port Open Browser uses. Nothing is drawn before the first start has been reported, so normal startup is unchanged. The observer is removed on exit. In the recovery state the footer reads *The server is not running. Choose an action above.*; the normal footer text is unchanged. `tests/launcher_port_driver.py` d1_* scenarios drive Settings-equivalent moves against the real window.

**Restart.** Save and Restart persists, then (after the response is delivered) `PortController._restart_now`: (1) stop the server and release the port, (2) spawn a fresh instance (`build_relaunch_command`: source = interpreter + script, frozen = the executable; a `--port=` override is dropped; frozen children get `PYINSTALLER_RESET_ENVIRONMENT=1` so a one-file build re-extracts), (3) the launcher leaves. If the spawn fails the old server is started again on the same port. The relaunched instance therefore never collides with the old one, including when the chosen port equals the one the old instance held. The Remote Access listener, if on, is released when the old process exits; the new instance restores it on start as always.

**Backup.** `local_port.json` is listed in `luma_backup.EXCLUDED` and is not a section: a replacement PC has different free ports, and an authoritative restore must not impose this machine's port. `tests/test_local_port.py` asserts it is excluded.

**Logging.** INFO events only (conflict, alternate chosen, port changed, restart); nothing periodic; no secrets.

**Tests.** `tests/test_local_port.py` (controller, file, routes; real loopback sockets), `tests/test_launcher_port.py` + `tests/launcher_port_driver.py` (the real `AppWindow` under a withdrawn Tk root, driven with `btn.invoke()`; skipped loudly when Tk cannot initialise), `tests/port_settings_test.js` (render path and request contract), mutations `port.*` in `tests/mutate_security.py`.


## 38. Restricted routing: no page-wide lock, and a route is only ever what it has been shown to be

Found on hardware against the v1.1.0 draft: after one route the Routing and Matrix pages refused every further route until
verification and a full state read had finished, and a display that was merely slow to report the stream it had taken was
drawn as a failure (a red mark) and then corrected by the next refresh. Both were in `ui/user.js`; the server was already
parallel and per-display locked.

- **The page holds only what it is writing to.** `state.routing` is per target (display, group, wall, matrix row); there is
  no page-wide busy flag. A second route to a *different* target goes straight out; a second route to the *same* target
  waits for the first (`Still routing`). The server's per-display locks remain the authority.
- **One state read per burst.** `scheduleRefresh` runs when the last route in flight finishes, not after each one. Cards are
  updated in place (`paintCardState`); `render()` skips a rebuild when what the cards are drawn from has not changed.
- **Three states per destination, from the server.** `/api/user/route_multi` returns `targets` -- one per thing chosen, named
  by *position* in the list the page sent (the response carries no identity) -- each `verified`, `unconfirmed` or `failed`.
  `unconfirmed` is a video route whose read-back answered with another stream (`not_verified`); a group is the worst of its
  members. Audio-only routes and walls are never `unconfirmed`.
- **The later look is read-only.** `POST /api/user/route_check` (USER) takes the same grants a route needs, confirms each
  display's identity, and reads the encoder's stream and the decoder's selected stream. It writes nothing and takes no lock.
  The page looks at 1.5 s, 3 s and 5 s after the answer; a display that never reports the stream is then a verified failure.
  A later route to the same target replaces an earlier one's outcome (`routeToken`), so a late look cannot undo it.
- **Unconfirmed is drawn as neither success nor failure** (`route-pending`, `Confirming…`; matrix cell `pending`). Only a
  verified failure is red.
- Measurement tooling: `tests/bench_routing.py` (server, against `_devicesim`) and `tests/bench_user_ui.js` (the page, with
  answers delayed by the server figures). Real-hardware timings are a separate live step.
